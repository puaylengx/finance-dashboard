Authentication — Platform = SPA + Redirect URI ของ Popup Handler

Azure Portal
  1. ใน App ที่เพิ่ง register → เลือก Authentication จาก sidebar
  2. คลิก + Add a platform
  3. เลือก Single-page application (SPA)
ต้องเลือก SPA ไม่ใช่ Web — frontend ใช้ @azure/msal-browser (Authorization Code + PKCE) ทำงานใน browser โดยตรง ถ้าเลือก Web จะเจอ CORS error ตอน loginPopup()
PlatformFlowใช้ได้กับ MSAL Browser
SPA Single-page application Auth Code + PKCE (ไม่ต้อง client secret ฝั่ง browser) ✓ ถูกต้อง
Web Web application Auth Code + client secret (server-side) ✗ CORS error

ระบบนี้ใช้ popup flow (ไม่ใช่ redirect flow) — popup window จะโหลดหน้า auth-redirect.html ของ frontend เอง แล้วส่งผลลัพธ์กลับไปยังหน้าหลักผ่าน BroadcastChannel (ดู Step 8.4) ดังนั้น Redirect URI ที่ตั้งใน Azure ต้องชี้ไปที่ไฟล์นี้โดยตรง ไม่ใช่ origin เปล่า ๆ:

สภาพแวดล้อมRedirect URI

Staginghttps://staging.your-domain.com/auth-redirect.html
Productionhttps://your-domain.com/auth-redirect.html

Certificates & Secrets — สร้าง Client Secret

Azure Portal

Backend ต้องใช้ client secret เพื่อแลก token แทนผู้ใช้ (On-Behalf-Of) และเพื่อเรียก Microsoft Graph แบบ app-only — เป็น fallback สำหรับตอนที่ jobTitle ไม่ติดมาใน access token (ดู Step 7 และหัวข้อ jobTitle Resolution Chain)

  1. เลือก Certificates & secrets จาก sidebar
  2. คลิก + New client secret
  3. ตั้งชื่อ + อายุ (แนะนำ 6–12 เดือน แล้วตั้ง reminder ต่ออายุ)
  4. คลิก Add
คัดลอกค่าใน column "Value" ทันที — ไม่ใช่ "Secret ID" — ค่านี้จะแสดงครั้งเดียว ปิดหน้าไปแล้วดูซ้ำไม่ได้ ต้องสร้างใหม่ถ้าพลาด

ค่านี้คือ AZURE_CLIENT_SECRET ใน backend .env (ดู Step 7)

ไม่สร้าง secret นี้ได้ไหม? ได้ — ระบบยังทำงานได้ถ้า Entra token มี jobTitle claim ติดมาเอง (Step 6) หรือถ้า frontend ดึง jobTitle จาก Graph สำเร็จและส่งมาเป็น fallback แต่ทาง On-Behalf-Of (แนะนำที่สุด เพราะ permission scope แคบสุด) จะไม่ทำงาน

API Permissions — ให้สิทธิ์ที่จำเป็น

Azure Portal

เลือก API permissions จาก sidebar แล้วเพิ่มทั้งหมดนี้:

APIPermissionTypeเหตุผลจำเป็น?
Seamless Dashboard (ตัวเอง)access_as_userDelegatedtoken ที่ frontend ใช้คุยกับ backend✓ จำเป็น
Microsoft GraphopenidDelegatedOIDC login flow พื้นฐาน✓ จำเป็น
Microsoft GraphprofileDelegatedดึง name/claims พื้นฐานจาก Entra✓ จำเป็น
Microsoft GraphUser.ReadDelegatedใช้โดย frontend (ดึง jobTitle ตรงจาก browser) และ โดย backend OBO flow✓ จำเป็น
Microsoft GraphUser.Read.AllApplicationapp-only Graph fallback (backend ค้นหา jobTitle จาก oid โดยตรง) — ใช้เฉพาะตอน token claim และ OBO ใช้ไม่ได้ทางเลือก

วิธีเพิ่ม:

  1. access_as_user: คลิก + Add a permission → tab APIs my organization uses → ค้นหาชื่อ App ของตัวเอง (seamless-dashboard) → Delegated → ติ๊ก access_as_user
  2. openid / profile / User.Read: + Add a permission → Microsoft Graph → Delegated permissions → ค้นหาแล้วติ๊กทั้ง 3
  3. User.Read.All (ถ้าต้องการ app-only fallback): + Add a permission → Microsoft Graph → Application permissions → ค้นหา User.Read.All
Grant admin consent — คลิก Grant admin consent for [organization] แล้วกด Yes (ต้องมีสิทธิ์ Global Admin หรือ Application Admin)

User.Read (delegated) ต้อง consent ก่อนถึงจะใช้ On-Behalf-Of (Step 7) ได้สำเร็จ — ถ้าไม่ consent backend จะ log OBO token exchange failed แล้วตกไปลำดับถัดไปในการหา jobTitle

User.Read.All (application) ต้อง admin consent เสมอ ไม่ว่า user คนไหนจะ login ก็ตาม

หลัง grant — status column จะเปลี่ยนเป็น Granted for [org]

Token Configuration — เพิ่ม jobTitle Claim (แนะนำ แต่ไม่บังคับ)

Azure Portal

ถ้า access token มี jobTitle claim ติดมาด้วย backend จะใช้ค่านี้ทันทีโดยไม่ต้องเรียก Graph เพิ่ม (เร็วที่สุด ไม่มี network round-trip เพิ่ม) — แต่ถ้าข้ามขั้นนี้ ระบบยังทำงานได้ผ่าน On-Behalf-Of / app-only Graph fallback ใน Step 4–5

job_title ไม่ปรากฏในรายการ optional claim ของ UI — ต้องเพิ่มผ่าน Manifest (JSON) โดยตรง
  1. เลือก Manifest จาก sidebar
  2. ค้นหา key "optionalClaims" ใน JSON
  3. แก้ค่าเป็น:
"optionalClaims": {
    "idToken": [],
    "accessToken": [
        {
            "name": "job_title",
            "source": null,
            "essential": false,
            "additionalProperties": []
        }
    ],
    "saml2Token": []
},
  1. กด Save
ชื่อ claim ใน token คือ job_title (snake_case) — Backend รองรับทั้ง job_title และ jobTitle (ดู auth_service.py → claims.get("jobTitle") or claims.get("job_title"))

ทำไมต้องเป็น Access token ไม่ใช่ ID token?
Backend รับ access token จาก MSAL (scope access_as_user) แล้ว validate กับ Azure JWKS — claim ต้องอยู่ใน access token เดียวกันนี้

ตรวจสอบ claim ใน token — วาง access token ที่ได้จาก MSAL ที่ jwt.ms แล้วดูว่ามี field job_title ปรากฏหรือไม่

ถ้า login อยู่แล้ว → ต้อง logout แล้ว login ใหม่ เพื่อให้ Azure ออก token ใหม่ที่มี claim ครบ

Backend — ตั้งค่า .env

Backend

เปิดไฟล์ backend/.env แล้วใส่ค่าจาก Step 1–4:

# Microsoft Entra ID
AZURE_TENANT_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
AZURE_CLIENT_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
AZURE_CLIENT_SECRET=your-client-secret
AZURE_AUTHORITY=https://login.microsoftonline.com/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
ENTRA_DOMAIN=company.com

# ปิด Draft Mode เมื่อพร้อม production
DRAFT_MODE=false
APP_ENV=production
ตัวแปรใช้ทำอะไร / ใช้ที่ไหนในโค้ดบังคับ?
AZURE_TENANT_ID Directory (tenant) ID จาก Step 1 — ใช้สร้าง URL ดึง JWKS (.../discovery/v2.0/keys) สำหรับ verify signature ของ access token, และ URL ขอ token ตอน On-Behalf-Of / app-only Graph (auth_service.py) จำเป็น
AZURE_CLIENT_ID Application (client) ID จาก Step 1 — ใช้ตรวจ aud claim ของ token ที่ frontend ส่งมา (ต้องตรงกับ {client-id} หรือ api://{client-id}) ไม่ใช่ token นี้จะถูก reject จำเป็น
AZURE_CLIENT_SECRET จาก Step 4 — เปิดใช้ 2 fallback path ในการหา jobTitle: (1) On-Behalf-Of แลก access token ของผู้ใช้เป็น Graph token (ต้องการแค่ User.Read delegated), (2) app-only Graph ด้วย client_credentials (ต้องการ User.Read.All application + admin consent) ถ้าไม่ตั้งค่านี้ ระบบจะข้ามทั้ง 2 path และพึ่ง token claim หรือ frontend fallback เท่านั้น ทางเลือก แต่แนะนำให้ตั้ง
AZURE_AUTHORITY เก็บไว้สำหรับ config/documentation — ปัจจุบันโค้ด backend ยังไม่ได้อ่านค่านี้ไปใช้ตรง ๆ (สร้าง URL จาก AZURE_TENANT_ID เองทุกที่) ตั้งไว้ตามรูปแบบเผื่อใช้ในอนาคตได้ ไม่กระทบ flow ปัจจุบัน ไม่บังคับ
ENTRA_DOMAIN เช่น company.com — ใช้ตอน เพิ่ม coordinator ผ่าน /admin/coordinators: backend auto-build upn = username@ENTRA_DOMAIN เก็บคู่กับ username ใน finance_coordinator table เพื่อให้ตรงกับ preferred_username ที่ Entra ส่งมาตอน login จริง (ไม่ต้องให้แอดมินพิมพ์ UPN เต็มเอง) ทางเลือก — จำเป็นถ้าจะใช้ coordinator fallback แบบ UPN
DRAFT_MODE เปิด/ปิด endpoint /auth/draft-login ที่จำลองผลลัพธ์เดียวกับ Entra login โดยไม่ต้องต่อ Azure จริง (ใช้ dev/QA) true=เปิด, false=ปิด (404) ต้องเป็น false ใน production
APP_ENV=production + DRAFT_MODE=true → App จะ refuse to start
มี guard ใน config.py (validate_production_secrets) ที่ block combination นี้ไว้ ถ้ายังทดสอบอยู่ให้ใช้ APP_ENV=staging

Restart backend หลังแก้ไข .env:

cd backend
uvicorn app.main:app --reload
Backend validate token โดย fetch JWKS จาก:
https://login.microsoftonline.com/{AZURE_TENANT_ID}/discovery/v2.0/keys (cache ใน memory จนกว่า process restart, มี circuit breaker หยุดยิง 60s หลัง fail 3 ครั้งติด)
ตรวจ audience ทั้ง {CLIENT_ID} และ api://{CLIENT_ID} รูปแบบ

8.3 MSAL Config ปัจจุบัน

frontend/src/lib/msalConfig.ts:

const clientId = import.meta.env.VITE_AZURE_CLIENT_ID ?? ''
const tenantId = import.meta.env.VITE_AZURE_TENANT_ID ?? ''

export const isMsalConfigured = (): boolean => Boolean(clientId && tenantId)

const msalConfig: Configuration = {
  auth: {
    clientId,
    authority: `https://login.microsoftonline.com/${tenantId}`,
    redirectUri: window.location.origin,   // override เป็น /auth-redirect.html ตอนเรียก loginPopup()
  },
  cache: {
    cacheLocation: 'localStorage',  // MSAL token cache — แยกจาก auth session (sessionStorage)
  },
  system: {
    popupBridgeTimeout: 360_000,   // 6 นาที — เวลารอ user กรอกรหัสในหน้า popup
    iframeBridgeTimeout: 10_000,
  },
}

export const msalInstance = new PublicClientApplication(msalConfig)

export const loginScopes = {
  scopes: ['openid', 'profile', `api://${clientId}/access_as_user`],
}
cacheLocation: localStorage — token cache ของ MSAL เองอยู่ข้าม tab/restart browser (ปกติสำหรับ MSAL) ส่วน session ของแอป (JWT ที่ backend ออก) เก็บแยกใน sessionStorage ผ่าน auth/session.ts — ปิด tab แล้ว session ของแอปหายแม้ MSAL cache ยังอยู่

8.5 auth-redirect.html — Popup Bridge (จำเป็นต่อ loginPopup)

เป็นไฟล์ root-level แยกจาก index.html — ต้อง build เป็น entry point แยกใน vite.config.ts:

  rollupOptions: {
    input: {
      main: resolve(__dirname, 'index.html'),
      authRedirect: resolve(__dirname, 'auth-redirect.html'),  // ← ต้องมี ไม่งั้น dist/ ไม่มีไฟล์นี้

frontend/auth-redirect.html → โหลด src/auth-redirect.ts ซึ่งทำงานเฉพาะ "ใน popup window":

// src/auth-redirect.ts
import { BrowserUtils } from '@azure/msal-browser'

const { payload, libraryState } = BrowserUtils.parseAuthResponseFromUrl()
const channel = new BroadcastChannel(libraryState.id)
channel.postMessage({ payload, v: 1 })   // ส่งผลลัพธ์กลับไปยัง loginPopup() ในหน้าหลัก
channel.close()
window.close()   // ปิด popup เองหลังส่งเสร็จ
ถ้า deploy แล้วเจอ "popup ค้าง / ไม่ปิดเอง" หรือ login ไม่จบ ให้เช็คก่อนว่า https://your-domain/auth-redirect.html เข้าได้จริงและ Redirect URI ใน Azure (Step 2) ตรงกับ path นี้เป๊ะ

8.6 LoginView.vue — Login Handler ปัจจุบัน

เมื่อกดปุ่ม Microsoft login ระบบทำ 3 จังหวะ: ขอ token ของ API ตัวเอง → ขอ token ของ Graph แยก (silent) เพื่อดึง jobTitle ฝั่ง browser → ส่งทั้งสองให้ backend:

// LoginView.vue
async function handleMicrosoftLogin() {
  const result = await msalInstance.loginPopup({
    ...loginScopes,
    redirectUri: `${window.location.origin}/auth-redirect.html`,
    prompt: 'select_account',
  })

  // ดึง jobTitle ตรงจาก Graph ฝั่ง browser — ส่งไปเป็น fallback สุดท้าย (ดูหัวข้อ jobTitle chain)
  const graphToken = await msalInstance.acquireTokenSilent({
    scopes: ['https://graph.microsoft.com/User.Read'],
    account: result.account,
  })
  const profile = await fetch('https://graph.microsoft.com/v1.0/me?$select=jobTitle', {
    headers: { Authorization: `Bearer ${graphToken.accessToken}` },
  }).then(r => r.json())

  const session = await entraLogin(result.accessToken, profile.jobTitle ?? '')
  auth.setUser(session.token, session, result.account?.username ?? '')
  router.push('/budget')
}
entraLogin() อยู่ที่ frontend/src/api/auth.ts — ส่ง POST ไปยัง /api/v1/auth/entra-login ด้วย { access_token, job_title } ทั้งคู่ — job_title ที่ส่งมาจะถูกใช้ "ก็ต่อเมื่อ" backend resolve จาก token claim / OBO / app-only ไม่ได้เลย (ลำดับสุดท้าย)
interaction_in_progress error — เกิดเมื่อมี popup ค้างจาก attempt ก่อนหน้า โค้ดจะ clear sessionStorage key ที่ขึ้นต้นด้วย msal. แล้ว retry ให้อัตโนมัติ 1 ครั้ง

jobTitle Resolution Chain

Backend (auth_service.py → login_with_entra_token()) พยายามหา jobTitle ตามลำดับนี้ หยุดทันทีที่ได้ค่าไม่ว่าง:

#แหล่งข้อมูลต้องตั้งค่าอะไรค่า job_title_source ใน log
1Claim ในตัว access token เอง (jobTitle หรือ job_title)Step 6 (Manifest optional claim)token
2On-Behalf-Of — แลก access token ของผู้ใช้เป็น Graph token แล้วเรียก /me?$select=jobTitleAZURE_CLIENT_SECRET + Graph User.Read (delegated, consented)graph:obo
3App-only Graph — ใช้ client_credentials token เรียก /users/{oid}?$select=jobTitleAZURE_CLIENT_SECRET + Graph User.Read.All (application, admin consent)graph:app
4job_title ที่ frontend ส่งมาใน request body (ดึงจาก Graph ฝั่ง browser เอง)ไม่ต้องตั้งอะไรเพิ่ม — ทำงานถ้า frontend consent User.Read สำเร็จfrontend
ถ้าหาไม่ได้เลยทั้ง 4 ทาง → log Entra login denied: ... (job_title not found) และตอบ 403 ทันที (ไม่ไปเช็ค coordinator table ต่อ)

job_title → role / position Parsing

เมื่อได้ jobTitle มาแล้ว (ไม่ว่าจากแหล่งไหนใน 4 ข้อด้านบน) backend ส่งเข้า extract_claims() ใน app/core/security.py:

  • แยก string ด้วย , แล้วทำเป็นตัวพิมพ์เล็กทุก segment
  • ถ้า segment สุดท้ายอยู่ใน {chief, chairman, head} → นั่นคือ position, segment ก่อนหน้าคือ role
  • ถ้าไม่ใช่ → ไม่มี position, segment สุดท้ายคือ role เลย
jobTitle ตัวอย่างrolepositionผลลัพธ์
fafa—ไม่มี position → ต้องเป็น coordinator จึงเข้าได้
fa,chieffachiefเข้าได้ทันที (มี position)
staff,bbabba—ไม่มี position → ต้องเป็น coordinator จึงเข้าได้
staff,bba,headbbaheadเข้าได้ทันที (มี position)
faculty,ft_lecturers,sc,chairmanscchairmanเข้าได้ทันที (รองรับ 4 segments — position ดูจากตัวสุดท้ายเสมอ)
Logic ไม่ได้ผูกกับชื่อ department ตายตัว — รับ string รูปแบบใดก็ได้ตราบใดที่ position (ถ้ามี) อยู่ segment สุดท้าย จำนวน segment ก่อนหน้าไม่ถูกจำกัด ฝั่ง frontend draft-login form สร้าง string เหล่านี้ให้ตรง format อยู่แล้ว (ดู jobTitlePreview ใน LoginView.vue) — ใน Entra ID จริง ค่า jobTitle ของ user ใน Azure Portal ต้องตั้งให้ตรง format นี้เอง

วิธีตั้งค่า jobTitle ของ User ใน Azure Portal

  1. ไปที่ Entra ID → Users
  2. คลิกชื่อ user ที่ต้องการ
  3. คลิก Edit properties (ปุ่มดินสอบนสุด)
  4. เลื่อนหา field Job title
  5. ใส่ค่าตามรูปแบบ เช่น fa,chief
  6. กด Save

Coordinator Fallback (ไม่มี position)

ถ้า jobTitle parse แล้วไม่มี position (เช่น fa หรือ staff,bba เพียว ๆ) backend จะเช็คอีกทางก่อนปฏิเสธ — ค้นหา username ใน table finance_coordinator (ดู auth_service.is_coordinator()):

SELECT 1 FROM finance_coordinator
WHERE (LOWER(upn) = LOWER(:username) OR LOWER(username) = LOWER(:username))
  AND active = TRUE
  • เทียบกับทั้ง upn และ username column — รองรับทั้งกรณี admin ใส่แค่ local part กับกรณีที่มี ENTRA_DOMAIN ตั้งไว้แล้ว auto-build เป็น UPN เต็ม (username@domain)
  • ผลลัพธ์ cache ใน Redis (REDIS_TTL_COORDINATOR, default 600s) ลด query ซ้ำ
  • ถ้า match และ active = TRUE → ออก JWT พร้อม coordinator: true (role ยังเป็นค่าที่ extract ได้จาก jobTitle เดิม ไม่ถูก override)
Frontend router guard (router/index.ts) บล็อกเส้นทางที่ requiresAuth ถ้า role === 'user' && !coordinator — หมายความว่า user ที่ jobTitle parse ไม่ได้รูปแบบที่รู้จักเลย (role กลายเป็น 'user' default) จะเข้าไม่ได้นอกจากเป็น coordinator ที่ active อยู่ในตาราง

เพิ่ม coordinator ผ่าน Admin UI หรือเรียก API ตรง:

POST /api/v1/admin/coordinators
{ "username": "john.doe" }
→ ถ้าตั้ง ENTRA_DOMAIN=company.com backend จะเซ็ต upn = "john.doe@company.com" ให้อัตโนมัติ

Troubleshooting

!

CORS error ตอน loginPopup()

สาเหตุ: เลือก Platform เป็น Web แทน SPA

วิธีแก้: Azure Portal → App registration → Authentication → ลบ Web platform → Add platform → เลือก Single-page application

!

"AADSTS65001" / scope ถูกปฏิเสธตอน loginPopup()

สาเหตุ: ยังไม่ทำ Step 3 (Expose an API) หรือยังไม่ grant consent ให้ access_as_user

วิธีแก้: ตรวจ Expose an API ว่ามี scope access_as_user ตั้งอยู่ แล้วไปหน้า API permissions ว่ามี permission ของ app ตัวเองอยู่และ Granted แล้ว

!

Popup ค้าง ไม่ปิดเอง / login ไม่จบ

สาเหตุ: auth-redirect.html ไม่ถูก build หรือ deploy, หรือ Redirect URI ใน Azure ไม่ตรงกับ path จริง

วิธีแก้: เปิด https://your-domain/auth-redirect.html ตรง ๆ ดูว่าโหลดได้ และเช็ค vite.config.ts ว่ามี authRedirect entry ใน rollupOptions.input แล้ว rebuild

!

Backend ตอบ 503 — "MS Entra ID ยังไม่ได้ตั้งค่า"

สาเหตุ: AZURE_TENANT_ID หรือ AZURE_CLIENT_ID ใน .env ว่างอยู่

วิธีแก้: ตรวจสอบ backend/.env ให้ครบ แล้ว restart backend

grep AZURE backend/.env
!

Backend log "OBO token exchange failed" / "OBO Graph /me failed"

สาเหตุ: AZURE_CLIENT_SECRET หมดอายุ/ผิด, หรือ Graph User.Read (delegated) ยังไม่ได้ grant admin consent

วิธีแก้: สร้าง client secret ใหม่ (Step 4), ตรวจ API permissions ว่า User.Read delegated สถานะ Granted (Step 5) — ระบบจะตกไป fallback ถัดไปอัตโนมัติ ไม่ทำให้ login fail ทันที เว้นแต่ทุก fallback ใช้ไม่ได้

!

Backend ตอบ 403 — "ไม่มีสิทธิ์เข้าถึง"

สาเหตุ: หา jobTitle ไม่พบเลยจากทั้ง 4 ทาง (ดู jobTitle Resolution Chain) หรือพบแล้วแต่ parse ออกมาไม่มี position และ user ไม่อยู่ใน finance_coordinator

วิธีแก้:

  1. ตรวจสอบ jobTitle ของ user ใน Entra ID ตามรูปแบบในหัวข้อ Parsing
  2. หรือเพิ่ม username เข้า finance_coordinator table ด้วย active = TRUE
-- เพิ่ม coordinator ตรง DB (หรือใช้ POST /api/v1/admin/coordinators)
INSERT INTO finance_coordinator (username, upn, active)
VALUES ('john.doe', 'john.doe@company.com', TRUE);
!

App จะ refuse to start — "DRAFT_MODE must be false"

สาเหตุ: ตั้ง APP_ENV=production แต่ DRAFT_MODE=true พร้อมกัน

วิธีแก้: ถ้าจะใช้ production → ตั้ง DRAFT_MODE=false
ถ้ายังทดสอบอยู่ → ตั้ง APP_ENV=staging
