Data Management — 10 requirements   Pass 5 / Partial 3 / Fail 2

การจัดการ database, caching, migration, และความสมบูรณ์ของข้อมูล

1. PostgreSQL (SSH/Direct)
รองรับการเชื่อมต่อทั้งแบบ SSH tunnel และ direct connection
P1Pass

คืออะไร

รองรับการเชื่อมต่อ PostgreSQL ได้ 2 วิธี: Direct เชื่อมตรงผ่าน network, SSH Tunnel เชื่อมผ่าน SSH jump server ก่อนแล้วค่อย forward ไปยัง DB ซึ่งอยู่ใน private network ที่ไม่ expose internet โดยตรง

ทำไมถึงสำคัญ

Production DB มักอยู่ใน private network ที่เข้าถึงได้ผ่าน SSH เท่านั้น เพื่อความปลอดภัย การที่ app รองรับทั้งสองแบบทำให้ dev ใช้ direct ได้ง่าย ส่วน prod ใช้ SSH ได้ตาม network policy

สถานะในโปรเจกต์ ✓

DB_MODE=ssh|direct ใน .env · SSH ผ่าน sshtunnel + paramiko รองรับ key-based และ password auth · database.py:19-67

2. Database Indexing
ทำ index บน column ที่ใช้ filter/join บ่อย
P1Pass

คืออะไร

Database index คือโครงสร้างข้อมูลเพิ่มเติมที่ทำให้ DB ค้นหาแถวที่ต้องการได้เร็วขึ้นมาก แทนที่จะ scan ทุกแถว (sequential scan) ใช้ B-tree index ค้นได้ใน O(log n) ซึ่งแตกต่างมากเมื่อมีหลายล้านแถว

ทำไมถึงสำคัญ

Finance query ของ system นี้ทำ JOIN หลาย table และ WHERE ด้วย fiscal_year, cost_owner, gl_id ทุก query ถ้าไม่มี index แต่ละ query อาจใช้เวลาหลายวินาทีแทนที่จะเป็น milliseconds

สถานะในโปรเจกต์ ✓

migrations/004_create_indexes.sql มี 16 indexes ครอบคลุม: fiscal_year, fiscal_year+fiscal_month, year+month, gl_id, cost_ctr_id, cost_owner, IO fields (partial indexes สำหรับ nullable columns), master table PKs

3. Data Integrity
ใช้ DB constraint (NOT NULL, FK, CHECK) และจัดการ transaction ด้วย ACID
P1Pass

คืออะไร

Data integrity คือการรับประกันว่าข้อมูลใน DB ถูกต้องและสอดคล้องกันเสมอ ทำได้ด้วย constraint (NOT NULL, UNIQUE, FK, CHECK) และ ACID transaction (Atomicity, Consistency, Isolation, Durability)

ทำไมถึงสำคัญ

ถ้าไม่มี constraint อาจมี coordinator record ที่ username เป็น NULL, หรือ ERP record ที่ amount เป็น NULL ซึ่งทำให้ aggregate calculation ผิด ข้อมูลการเงินผิดพลาดสร้างความเสียหายทางธุรกิจ

สถานะในโปรเจกต์ ✓

Coordinator table: NOT NULL ทุก required field, UNIQUE(username), DEFAULT TRUE · ERP table: implicit NOT NULL ผ่าน data import · psycopg3 transaction: auto rollback เมื่อ exception ใน async with get_db()

4. Redis Caching
Cache ข้อมูลที่เรียกบ่อย พร้อมกำหนด TTL ที่เหมาะสม
P1Pass

คืออะไร

Redis คือ in-memory data store ที่ใช้เป็น cache layer ระหว่าง application และ database ข้อมูลที่ query บ่อยและเปลี่ยนแปลงไม่บ่อยจะถูกเก็บใน Redis ซึ่งเร็วกว่า DB หลายร้อยเท่า TTL (Time To Live) กำหนดว่า cache หมดอายุเมื่อไร

ทำไมถึงสำคัญ

Finance SQL ของ system นี้ซับซ้อนมาก (CTE + หลาย JSONB_AGG) ถ้าทุก request query DB จะช้าและ DB รับ load สูง Redis cache ทำให้ request ที่ 2 เป็นต้นไปตอบได้ใน milliseconds และ DB ทำงานน้อยลงมาก

สถานะในโปรเจกต์ ✓

Finance/Budget/IO: TTL 300s (5 min) · Coordinator lookup: TTL 600s (10 min) · cache key: seamless:v1:{prefix}:{role}:{params_hash} · graceful fallback เมื่อ Redis ไม่พร้อม — app ทำงานต่อได้โดยไม่มี cache

5. Connection Pooling
ใช้ connection pool ป้องกัน DB connection exhaustion
P1Pass

คืออะไร

Connection pool คือ pool ของ DB connection ที่สร้างไว้ล่วงหน้า แทนที่จะสร้าง connection ใหม่ทุก request (ซึ่งช้า) app หยิบ connection จาก pool มาใช้แล้วคืนกลับ ป้องกัน DB รับ connection เกิน limit

ทำไมถึงสำคัญ

PostgreSQL รองรับ connection จำนวนจำกัด (default 100) ถ้า app สร้าง connection ใหม่ทุก request ภายใต้ traffic สูงจะ exhaust limit ทำให้ DB reject connection ใหม่ทั้งหมด

สถานะในโปรเจกต์ ✓

psycopg3 AsyncConnectionPool min=2, max=20 · ปรับได้ผ่าน DB_POOL_MIN_SIZE, DB_POOL_MAX_SIZE · database.py:55-62 · async — ไม่ block event loop ขณะรอ connection

6. Read Replica
แยก read traffic ไปยัง PostgreSQL read replica เพื่อลดภาระ primary DB
P3Defer

คืออะไร

Read replica คือ PostgreSQL instance ที่ sync ข้อมูลจาก primary แบบ real-time (streaming replication) สำหรับ read-only query เท่านั้น ทำให้ primary DB รับเฉพาะ write operation ลด load ได้มาก

ทำไมถึงสำคัญ

Finance dashboard มีเฉพาะ read query (SELECT) เกือบทั้งหมด ถ้า concurrent users มากขึ้นจน primary DB เริ่ม overload read replica จะช่วยกระจาย load ได้โดยไม่ต้องเปลี่ยน code มาก

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

ยังไม่ได้ deploy · ผู้ใช้งานไม่มาก · Redis cache (TTL 300s) ช่วยลด read load ได้เพียงพอสำหรับ load ปัจจุบัน — ทบทวนเมื่อ concurrent users สูงขึ้นจริงหรือมี cache miss บ่อย

เมื่อถึงเวลา (trigger: DB load สูง / cache miss บ่อย)

  • ตั้ง PostgreSQL streaming replication: primary → replica
  • เพิ่ม READ_REPLICA_HOST ใน config (ค่า default = primary host ถ้ายังไม่มี replica)
  • เพิ่ม get_read_db() ใน database.py ที่ fallback ไป primary pool อัตโนมัติ
  • Route Finance/IO/Budget queries ไปยัง get_read_db()
7. Database Migration
ใช้ Alembic จัดการ schema migration แบบ version-controlled
P2Partial

คืออะไร

Database migration คือกระบวนการเปลี่ยน DB schema อย่างมีระเบียบผ่าน versioned files เช่น 001_add_column.sql Alembic คือ migration tool มาตรฐานของ Python/SQLAlchemy ที่รองรับ up (apply) และ down (rollback) migration

ทำไมถึงสำคัญ

ถ้าแก้ DB โดยตรงโดยไม่มี migration file ทีม dev จะไม่รู้ว่า production DB มี schema อะไรบ้าง เมื่อ deploy ใหม่ DB จะไม่ match code ทำให้ error down migration ทำให้ rollback เมื่อ deploy ใหม่มีปัญหาได้

สถานะในโปรเจกต์

มี custom migrations/migrate.py + raw SQL files (001-004) ✓ — idempotent ผ่าน IF NOT EXISTS, track ด้วย schema_migrations table ✓

แต่: ไม่ใช้ Alembic — ไม่มี down migration (rollback ไม่ได้) · ต้องเขียน SQL เอง ไม่มี auto-generate จาก model

สิ่งที่ต้องทำ

  • ถ้าต้องการ rollback: เพิ่ม down section ใน migration files แต่ละไฟล์
  • พิจารณา migrate ไปใช้ Alembic เพื่อ auto-generate migration จาก SQLAlchemy models
  • อย่างน้อย document ว่าแต่ละ migration undo ได้อย่างไร
8. Soft Delete
ใช้ is_deleted flag แทน hard delete เพื่อรักษา audit trail
P2Partial

คืออะไร

Soft delete คือการ "ลบ" ข้อมูลโดยการ set flag is_deleted=true แทนการลบ row จริง ข้อมูลยังอยู่ใน DB สามารถ restore ได้ ตรงข้ามกับ hard delete ที่ DELETE FROM table โดยตรง

ทำไมถึงสำคัญ

สำหรับ financial data การลบข้อมูลถาวรเป็น risk ถ้า hard delete ผิดพลาดจะกู้คืนไม่ได้ soft delete ยังรักษา audit trail ว่าเคยมีรายการนี้อยู่ และสามารถ restore ได้เมื่อ admin ต้องการ

สถานะในโปรเจกต์

finance_coordinator: ใช้ active BOOLEAN DEFAULT TRUE (soft delete) ✓ — PATCH /coordinators/{id} toggle active/inactive แทนการลบจริง

ERP data (erp_2025): ไม่มี soft delete — เป็น read-only import data จาก ERP system ดังนั้นไม่ apply

9. Database Backup
ทำ full backup รายวัน + incremental รายชั่วโมง + PITR รองรับย้อนหลัง 30 วัน
P2Fail

คืออะไร

Full backup คือ snapshot ทั้ง database ณ เวลาหนึ่ง Incremental backup คือ backup เฉพาะ changes หลัง backup ครั้งล่าสุด PITR (Point-in-Time Recovery) คือความสามารถ restore DB ไปยังช่วงเวลาใดก็ได้ในอดีต

ทำไมถึงสำคัญ

ถ้า DB crash, hardware failure, หรือ ransomware — ถ้าไม่มี backup ข้อมูลการเงินทั้งหมดหาย PITR ช่วยให้ restore ได้ถึง 1 นาทีก่อนเกิดปัญหา แทนที่จะต้องย้อนไปถึง full backup ล่าสุด

สถานะในโปรเจกต์ — ยังไม่มี

ไม่มี backup script · ไม่มี backup schedule · ไม่มี restore procedure document เป็น infrastructure gap ที่ต้องจัดการนอก codebase

สิ่งที่ต้องทำ

  • ตั้ง pg_dump cron job: full backup รายวัน (เก็บ 30 วัน), incremental ด้วย WAL archiving รายชั่วโมง
  • เก็บ backup ใน object storage แยก server (S3, Azure Blob) ไม่เก็บบน DB server เดียวกัน
  • Enable PostgreSQL WAL archiving สำหรับ PITR
  • ทดสอบ restore ทุก quarter เพื่อยืนยันว่า backup ใช้งานได้จริง
10. Data Retention Policy
กำหนด policy ว่าข้อมูลแต่ละประเภทเก็บนานเท่าไร ก่อน archive หรือ purge
P3Fail

คืออะไร

Data retention policy คือ rule ที่กำหนดว่าข้อมูลแต่ละประเภทต้องเก็บอย่างน้อยกี่ปี และเมื่อครบกำหนดต้องทำอะไร (archive ลง cold storage, anonymize, หรือ delete) เพื่อสมดุลระหว่าง compliance requirement และ storage cost

ทำไมถึงสำคัญ

ข้อมูลการเงินในไทยต้องเก็บตาม กฎหมายบัญชี อย่างน้อย 5 ปี ถ้าเก็บมากเกินไปก็เปลืองพื้นที่และเพิ่มความเสี่ยง ถ้าเก็บน้อยเกินไปก็ผิด compliance

สถานะในโปรเจกต์ — ยังไม่มี

erp_2025 table ชื่อระบุปีไว้ชัดเจน แต่ไม่มี policy ว่าเมื่อไรจะ archive หรือ create erp_2026 ไม่มีกระบวนการ purge coordinator records เก่า

สิ่งที่ต้องทำ

  • กำหนด retention period: ERP data เก็บ 7 ปี (financial compliance), coordinator records เก็บ 2 ปีหลัง inactive
  • สร้าง archive process: ข้อมูลเก่า → cold storage (เช่น Azure Archive Tier)
  • Document policy และ review ทุกปี
