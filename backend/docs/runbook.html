1. Restart API Service

ขั้นตอน — Docker Compose

# ตรวจสถานะก่อน restart
docker compose ps
docker compose logs api --tail=20

# Graceful restart (รอ request ที่ค้างอยู่ก่อน)
docker compose restart api

# ถ้า restart ไม่ได้ผล — force recreate
docker compose up -d --force-recreate api

# ตรวจหลัง restart
curl http://localhost:8000/health
# คาดหวัง: {"status":"ok"}

ขั้นตอน — uvicorn โดยตรง

# หา process
ps aux | grep uvicorn

# ส่ง SIGTERM (graceful shutdown — รอ request ที่ค้าง)
kill -TERM <PID>
# รอ log "Shutdown complete" ก่อน process exit

# เริ่มใหม่
cd backend
source .venv/bin/activate
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2 &

# ตรวจ
curl http://localhost:8000/health

สิ่งที่ต้อง check หลัง restart

  • /health ต้อง 200 ภายใน 15 วินาที
  • /ready ต้อง 200 (DB + Redis พร้อม)
  • ดู log ว่าไม่มี ERROR ใน 1 นาทีแรก

3. Redis Down / Connection Refused

Symptoms

  • /ready ตอบ 503 {"failing":["redis"]}
  • Log มี "Cache get error" หรือ "Cache set error" บ่อยๆ
  • Dashboard ยัง load ได้แต่ช้าลง (cache miss ทุก request)
  • API ไม่ crash — graceful degradation ทำงาน

Immediate Action

# ตรวจ Redis process
docker compose ps redis
# หรือ
redis-cli ping
# คาดหวัง: PONG

# Restart Redis
docker compose restart redis

# ตรวจหลัง restart (รอ 5 วินาที)
curl http://localhost:8000/ready
# คาดหวัง: {"status":"ok"}

# ถ้า restart ไม่ได้ผล — check disk space (Redis ใช้ RDB dump)
df -h
docker compose logs redis --tail=30

Escalation

ถ้า restart Redis ไม่ได้ผลใน 5 นาที: ติดต่อ developer
ระหว่างรอ: API ยังทำงานได้ปกติ (cache miss → query DB โดยตรง) แต่ load บน DB จะสูงขึ้น

High

4. DB Connection Error / SSH Tunnel Down

Symptoms

  • /ready ตอบ 503 {"failing":["db"]}
  • Finance dashboard ตอบ 500 Internal Server Error
  • Log มี "connection pool exhausted" หรือ "SSH tunnel" error
  • /health ยังตอบ 200 (liveness ไม่ตรวจ DB)

ขั้นตอน

# Step 1: ตรวจ readiness
curl http://localhost:8000/ready

# Step 2: ตรวจ SSH tunnel (ถ้า DB_MODE=ssh)
# — ดู log หา "SSH tunnel" หรือ "Connection refused"
grep -i "ssh\|tunnel\|connection" backend/logs/app.log | tail -10

# Step 3: ทดสอบ SSH connection โดยตรง
ssh -i /path/to/key deploy-user@jump.server.com "echo OK"

# Step 4: ถ้า SSH OK แต่ DB ไม่ได้ — ตรวจ DB server
ssh -i /path/to/key deploy-user@jump.server.com \
  "psql -h db-host -U postgres -c 'SELECT 1'"

# Step 5: Restart API (pool จะ reconnect)
docker compose restart api

# ตรวจหลัง restart
curl http://localhost:8000/ready

Escalation

ถ้าตรวจแล้ว SSH OK และ DB ตอบได้ แต่ API ยัง 503: ติดต่อ developer ทันที
ถ้า DB server down จริง: ติดต่อ DBA / infrastructure team

High

5. Error Rate สูง (5xx จำนวนมาก)

Symptoms

  • Users report "หน้าเว็บโหลดไม่ได้" หรือ "ข้อมูลไม่แสดง"
  • Log เต็มไปด้วย ERROR entries
  • Prometheus metrics: http_requests_total{status=~"5.."} สูง

ขั้นตอน Triage

# 1. ตรวจ error type
grep '"level":"ERROR"' backend/logs/app.log | tail -20 | python3 -c "
import sys, json
for line in sys.stdin:
    try:
        d = json.loads(line)
        print(d.get('ts',''), d.get('msg',''))
    except: print(line.strip())
"

# 2. ตรวจ health/ready
curl http://localhost:8000/health
curl http://localhost:8000/ready

# 3. ตรวจว่า error เริ่มหลัง deploy ล่าสุดหรือไม่
git -C /path/to/repo log --oneline -5

# 4. ดู Prometheus metrics
curl http://localhost:8000/metrics | grep http_requests_total

ถ้าเกิดหลัง deploy ใหม่ → Rollback

ดูขั้นตอน rollback ที่ Scenario 6

Critical

6. Rollback เมื่อ Deploy พัง

App Rollback (Docker)

# Step 1: ดู image versions ที่มี
docker images seamless-dashboard-api --format "table {{.Tag}}\t{{.CreatedAt}}"

# Step 2: แก้ image tag ใน docker-compose.yml เป็น version ก่อนหน้า
# image: seamless-dashboard-api:<previous-git-sha>

# Step 3: Deploy image เก่า
docker compose up -d api

# Step 4: ตรวจ
curl http://localhost:8000/health
curl http://localhost:8000/ready

DB Migration Rollback (ถ้า migration ใหม่ทำให้พัง)

cd backend
python migrations/migrate.py --rollback

# ตรวจ migrations ที่ยัง apply อยู่
psql -d ic_finance -c \
  "SELECT filename, applied_at FROM schema_migrations ORDER BY id DESC LIMIT 5;"

Escalation

Rollback ต้องทำโดย developer เสมอ — ops team แจ้ง developer และเตรียม log + error message ให้พร้อม
