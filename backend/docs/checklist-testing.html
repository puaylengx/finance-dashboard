1. Unit Tests
ครอบคลุม service layer และ business logic ด้วย pytest และ coverage ≥ 80%
P1Pass

คืออะไร

Unit test คือการทดสอบ function หรือ class แต่ละตัวแยกอิสระ โดย mock dependencies ออก เช่น mock DB connection หรือ Redis เพื่อทดสอบเฉพาะ business logic ของ function นั้น ตรงๆ โดยไม่ต้องมี infra จริง

ทำไมถึงสำคัญ

Unit test ทำให้ developer มั่นใจว่า logic ที่เขียนถูกต้อง และ detect regression ได้เร็วเมื่อ refactor หรือ add feature ใหม่ ใน financial system สำคัญมากเพราะ bug ในการคำนวณตัวเลขส่งผลกระทบโดยตรงต่อการตัดสินใจ

สถานะในโปรเจกต์ ✓

7 unit test files, 124 test cases ครอบคลุม security, permissions, deps, cache, pagination, และ service layers

backend/tests/
  unit/
    test_security.py           # extract_claims, JWT, Fernet, params_hash (18)
    test_permissions.py        # POSITION_ROLES, DIVISION_ROLES, ILIKE_ROOT_OVERRIDE (7)
    test_deps.py               # JWT dependency, valid/expired/invalid token (18)
    test_cache_service.py      # get_cached, set_cached, invalidate — Redis paths (16)
    test_pagination.py         # PaginationParams, PaginatedResponse, _apply_top_n (22)
    test_finance_service.py    # _build_params, _run_query, get_dashboard, get_io (32)
    test_coordinator_service.py # _row_to_dict, add, toggle — commit + cache (11)
  conftest.py                  # fixtures: mock DB, mock Redis, tokens

วิธีรัน

cd backend

# รัน unit tests ทั้งหมด
pytest tests/unit/ -v

# รันพร้อม coverage report
pytest tests/unit/ -v --cov=app --cov-report=term-missing
# คาดหวัง: coverage >= 80%

# รัน test file เดียว
pytest tests/unit/test_security.py -v

# รัน test case เดียว
pytest tests/unit/test_deps.py::test_valid_token -v

ผลที่คาดหวัง: 124 passed ไม่มี FAILED หรือ ERROR

2. Integration Tests
ทดสอบ API endpoint จริงกับ test database ด้วย pytest-asyncio และ httpx.AsyncClient
P1Pass

คืออะไร

Integration test ทดสอบหลาย component ทำงานร่วมกัน เช่น ส่ง HTTP request จริงไปยัง FastAPI endpoint ซึ่ง query test database จริง ตรวจสอบว่า layer ต่างๆ integrate กันได้ถูกต้อง ไม่ใช่แค่ unit แยกๆ

ทำไมถึงสำคัญ

Unit test mock ทุกอย่างออก แต่ integration test จับ bug ที่เกิดจาก interface ระหว่าง layer เช่น SQL query ที่ unit test mock ผ่านแต่ query จริงพัง เพราะ column name ผิด หรือ auth middleware ไม่ตรงกับ endpoint ที่คาดหวัง

สถานะในโปรเจกต์ ✓

3 integration test files, 59 test cases — ทดสอบ HTTP endpoint จริงด้วย httpx.AsyncClient + ASGITransport โดย mock DB/Redis

backend/tests/
  integration/
    test_auth.py         # /auth/login, /auth/entra-login, draft-login, /me (12)
    test_finance.py      # /finance, /budget, /io — auth, role, top_n, 500 (18)
    test_coordinator.py  # list (paginated, filters), add, toggle — SQL pagination logic (29)

วิธีรัน

cd backend

# รัน integration tests ทั้งหมด
pytest tests/integration/ -v

# รัน test auth endpoint เฉพาะ
pytest tests/integration/test_auth.py -v -s

# รันทุก test พร้อมกัน (unit + integration)
pytest tests/ -v --tb=short

# รัน tests เฉพาะที่ชื่อมีคำว่า "login"
pytest tests/ -k "login" -v

ผลที่คาดหวัง: 59 passed ไม่มี FAILED · Integration tests ใช้ httpx.AsyncClient + ASGITransport ไม่ต้องรัน server จริง

หมายเหตุ: integration tests mock DB/Redis — ไม่ต้องมี PostgreSQL/Redis running

3. Load Testing
ทดสอบ performance ด้วย k6 หรือ Locust เพื่อหา bottleneck และกำหนด capacity
P3Defer

คืออะไร

Load testing คือการจำลอง concurrent users จำนวนมากส่ง request พร้อมกัน เพื่อ: (1) หา throughput สูงสุดที่ system รองรับได้ (2) หา bottleneck (DB, Redis, CPU) (3) ตรวจสอบ response time ว่าอยู่ใน SLA ภายใต้ load จริง

ทำไมถึงสำคัญ

ระบบอาจ perform ดีตอน dev (1-2 concurrent users) แต่พังตอน production เมื่อมีหลายสิบ users พร้อมกัน load test ช่วย identify ปัญหาก่อน go-live เช่น DB connection pool exhausted, Redis timeout, หรือ memory leak

Defer — ต้องรันกับ server จริง

Load test ต้องรัน server จริงพร้อม production-like data และ infrastructure ทำในขั้นตอน pre-production/staging ก่อน go-live ไม่ใช่ในระหว่างพัฒนา

เมื่อ staging พร้อม ให้ดำเนินการ:

  • ติดตั้ง Locust (Python — ใช้ venv เดิมได้): pip install locust
  • เขียน load_tests/locustfile.py — scenario: GET /api/v1/finance ด้วย 50 concurrent users นาน 5 นาที
  • กำหนด success criteria: p95 response time < 2 วินาที, error rate < 1%
  • ตรวจสอบ Redis cache hit/miss ratio ภายใต้ load
  • ตรวจสอบ DB connection pool behavior (pool_size ใน database.py)

วิธีทดสอบ (เมื่อพร้อม)

# ติดตั้ง Locust
pip install locust

# เขียน load_tests/locustfile.py แล้วรัน
locust -f load_tests/locustfile.py \
  --host http://staging.internal:8000 \
  --users 50 --spawn-rate 5 --run-time 5m --headless

# ดู metrics ใน Prometheus + Grafana ระหว่าง load
# หรือ locust --web-ui ที่ port 8089
4. DB Query Performance Test
ทดสอบ SQL query performance ด้วย EXPLAIN ANALYZE เพื่อ detect slow query
P3Pass

คืออะไร

EXPLAIN ANALYZE เป็น PostgreSQL command ที่แสดง execution plan จริงของ query พร้อม actual time ใช้ชี้ให้เห็นว่า query ใช้ index หรือ Seq Scan, nested loop หรือ hash join และ actual vs estimated rows

ทำไมถึงสำคัญ

Finance dashboard ใช้ CTE query ซับซ้อนบน table ขนาดใหญ่ ถ้า query ไม่ใช้ index จะช้ามากเมื่อข้อมูลเพิ่มขึ้น ควรทดสอบ query time กับ dataset จริง ไม่ใช่แค่ dev data ที่มีน้อย row

สถานะในโปรเจกต์ ✓

  • EXPLAIN ANALYZE scripts: load_tests/explain_queries.sql — ครอบคลุม 7 scenarios: fiscal_year, fiscal_year+month, cost_ctr_id, full CTE, io_goods partial index, pg_stat_statements, และ index usage health check
  • pg_stat_statements migration: migrations/007_enable_pg_stat_statements.sql พร้อม postgresql.conf config แนะนำ (log_min_duration_statement = 200)
  • pytest performance tests: tests/performance/test_db_query_performance.py — 8 tests ครอบคลุม Index Scan verification, query execution time thresholds, และ pg_stat_statements availability
  • Marker: @pytest.mark.performance — exclude จาก default run, เปิดใช้ด้วย PERFORMANCE_TEST=1

วิธีทดสอบ

# 1. รัน EXPLAIN ANALYZE scripts กับ DB จริง
psql -d finance_db -f load_tests/explain_queries.sql
# ดู "Index Scan using idx_erp_fiscal_year" vs "Seq Scan"
# ถ้าเห็น Seq Scan: รัน ANALYZE erp_transactions; เพื่อ refresh statistics

# 2. Enable pg_stat_statements (ครั้งเดียว — ต้องมี superuser)
psql -d finance_db -f migrations/007_enable_pg_stat_statements.sql
# เพิ่มใน postgresql.conf:
#   shared_preload_libraries = 'pg_stat_statements'
#   log_min_duration_statement = 200

# 3. รัน performance pytest tests กับ DB จริง
PERFORMANCE_TEST=1 .venv/bin/python -m pytest tests/performance/ -v
# คาดหวัง:
#   test_fiscal_year_uses_index              PASSED
#   test_fiscal_year_month_uses_composite_index PASSED
#   test_cost_ctr_id_uses_index             PASSED
#   test_dashboard_cte_under_threshold       PASSED (< 3000 ms)

# 4. ตรวจ slow queries หลังมี traffic
psql -d finance_db -c "
  SELECT LEFT(query,80), calls, ROUND(mean_exec_time::numeric,2) AS avg_ms
  FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 5;"

# 5. ตรวจ index usage health (index ไหนไม่ถูกใช้)
psql -d finance_db -c "
  SELECT tablename, indexname, idx_scan
  FROM pg_stat_user_indexes
  WHERE tablename = 'erp_transactions'
  ORDER BY idx_scan DESC;"
