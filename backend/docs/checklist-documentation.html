1. Architecture Decision Records (ADR)
บันทึกการตัดสินใจด้าน architecture สำคัญ พร้อม context และ trade-off
P3Fail

คืออะไร

ADR คือ document สั้นๆ ที่บันทึกการตัดสินใจด้าน architecture แต่ละครั้ง ได้แก่: (1) Context — ทำไมถึงต้องตัดสินใจ (2) Decision — ตัดสินใจอะไร (3) Consequences — ผลที่ตามมา ทั้ง positive และ negative ตัวอย่าง: "ทำไมถึงเลือก Redis แทน Memcached" หรือ "ทำไมถึงใช้ psycopg3 แทน SQLAlchemy"

ทำไมถึงสำคัญ

6 เดือนต่อมา developer ใหม่ (หรือตัวเองก็ตาม) จะไม่รู้ว่าทำไมถึงเลือก design นี้ และอาจ refactor ออกไปโดยไม่รู้ว่า design เดิมมี reason ที่ดี ADR เก็บ "ความรู้ที่อยู่ในหัว" ให้ทีมทุกคนเข้าถึงได้

สถานะในโปรเจกต์ — ยังไม่มี

ไม่มี ADR directory หรือ document ใดๆ การตัดสินใจ architecture (เช่น SSH tunnel approach, Fernet encryption, DRAFT_MODE) ไม่ได้ถูก document ไว้

สิ่งที่ต้องทำ

  • สร้าง backend/docs/adr/ directory
  • เขียน ADR สำหรับ decision สำคัญที่มีอยู่แล้ว: SSH tunnel, Fernet encryption, Draft Mode, psycopg3 choice
  • ใช้ template: Title / Status / Context / Decision / Consequences
# backend/docs/adr/001-ssh-tunnel-db-connection.md
# Status: Accepted
# Context: Database อยู่บน internal network ไม่เปิด port ออก internet
# Decision: ใช้ SSH tunnel ผ่าน bastion host
# Consequences:
#   + ไม่ต้องเปิด DB port ออก internet (security)
#   - เพิ่ม latency เล็กน้อย, ต้องมี SSH key management
2. Developer Setup Guide
คู่มือ step-by-step ให้ developer ใหม่ setup local environment และรัน project ได้ภายใน 30 นาที
P2Pass

คืออะไร

Developer Setup Guide คือ document ที่บอก developer ใหม่ว่าต้องทำอะไรบ้างตั้งแต่ clone repo จนถึงรัน server ได้ รวมถึง: prerequisites, environment variables ที่ต้องตั้ง, วิธี run migrations, วิธีรัน dev server

ทำไมถึงสำคัญ

ถ้าไม่มี setup guide developer ใหม่ต้องใช้เวลาหลายวันถามคนโน้นคนนี้ เสียเวลาทั้งทีม ยิ่งถ้า developer เดิมลาออกไปแล้ว ความรู้นั้นหายไปด้วย

สถานะในโปรเจกต์ ✓

มี README.md หรือ backend/docs/backend.html ที่ cover การ setup project รวมถึง SSH config, environment variables, และวิธีรัน server

3. Runbook / Operations Guide
คู่มือสำหรับ ops team: วิธี restart service, วิธี check logs, วิธีจัดการ incident
P3Fail

คืออะไร

Runbook คือ document สำหรับ operations team (ไม่ใช่ developer) บอกวิธีจัดการ task routine และ incident เช่น: "วิธี restart API server", "วิธีดู error logs", "ถ้า Redis down ทำอะไร", "ถ้า DB connection pool exhausted ทำอะไร"

ทำไมถึงสำคัญ

เมื่อเกิด incident ตี 2 ops team ต้องจัดการได้โดยไม่ต้องโทรหา developer ถ้าไม่มี runbook ทุกปัญหาเล็กๆ กลายเป็นต้องรอ developer ซึ่งทำให้ MTTR (Mean Time To Recover) นานขึ้น

สถานะในโปรเจกต์ — ยังไม่มี

ไม่มี runbook หรือ operations guide ใดๆ

สิ่งที่ต้องทำ

  • เขียน runbook ครอบคลุม scenarios หลัก:
  • Restart service: command ที่ใช้, สิ่งที่ต้อง check หลัง restart
  • Check logs: log file อยู่ที่ไหน, format เป็นอย่างไร, วิธี filter error
  • Redis down: symptom, immediate action (restart), escalation path
  • DB connection error: ตรวจ SSH tunnel, ตรวจ DB status, วิธี reconnect
  • High error rate: วิธีดู Sentry dashboard, วิธี rollback ถ้าจำเป็น
4. Data Dictionary
อธิบาย schema ของทุก table, field name, data type และ business meaning
P3Partial

คืออะไร

Data Dictionary คือ document ที่อธิบายทุก table และ field ใน database ว่า: ชื่อคืออะไร, data type อะไร, และสำคัญที่สุด ความหมายทาง business คืออะไร เช่น gl_id ย่อมาจากอะไร, cost_ctr_id แตกต่างจาก cost_owner อย่างไร

ทำไมถึงสำคัญ

Database schema บอก technical structure แต่ไม่บอก business meaning developer ใหม่ต้องเดาว่า erp_transactions table มี column อะไรที่ relate กับ budget vs actual ถ้ามี data dictionary เข้าใจทันที

สถานะในโปรเจกต์ — บางส่วน

มี migration SQL files ที่แสดง table structure แต่ไม่มี document ที่อธิบาย business meaning ของแต่ละ field migration files อยู่ที่ backend/migrations/ แต่ไม่มี comment อธิบาย field

สิ่งที่ต้องทำ

  • สร้าง backend/docs/data-dictionary.html (หรือ markdown)
  • Document ทุก table: erp_transactions, cost_center_master, finance_coordinator และ master tables อื่นๆ
  • แต่ละ field ระบุ: ชื่อ, type, nullable, business meaning, ตัวอย่างค่า
  • ระบุ relationships: FK ไปยัง table ไหน, join ยังไง
