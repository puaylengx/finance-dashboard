Logging & Monitoring — 5 requirements   Pass 0 / Partial 5 / Fail 0

การ observe ระบบในเวลาจริง — หมวดนี้ยังต้องปรับปรุงมากที่สุด

1. Centralized Logging
ส่ง log ไปยัง Sentry / ELK Stack พร้อม structured JSON format
P2Partial

คืออะไร

Centralized logging คือการรวม log จากทุก server/container ไปเก็บที่ที่เดียว เพื่อให้ search, filter, และ analyze ได้ง่าย structured format (JSON) ทำให้ query ด้วย field เฉพาะได้ เช่น level=ERROR AND user=alice

ทำไมถึงสำคัญ

เมื่อมีหลาย server ไม่มีใครอยากเปิด SSH ไป grep log ทีละเครื่อง centralized logging ทำให้เห็นภาพรวมทันที สามารถ correlate event ข้าม service ได้ และตั้ง alert บน log pattern ได้

สถานะในโปรเจกต์ — บางส่วน

มีแล้ว: Rotating file log logs/app.log ✓ · Colored console output ✓ · Sentry integration (optional, เมื่อตั้ง SENTRY_DSN) ✓ · JSON file format ✓ — logging.py ใช้ _JsonFormatter เขียน {"ts","level","logger","msg"} ลง app.log

ยังไม่มี: Centralized platform (ELK / Datadog) — log ยังอยู่ใน local file เท่านั้น

สถานะ — เลื่อนไปก่อน (Intentional Defer)

ELK Stack / Datadog ต้องการ infrastructure แยก ยังไม่มี production deployment จริง · ทบทวนเมื่อ deploy multi-server หรือมี requirement ต้องค้นหา log ข้าม container

วิธีทดสอบ

# ตรวจ JSON format ใน log file
uvicorn app.main:app --reload &
curl -s http://localhost:8000/health
cat logs/app.log | tail -3
# คาดหวัง: {"ts":"2026-06-19T...","level":"INFO","logger":"app.main","msg":"..."}

# ตรวจ JSON parse ได้
cat logs/app.log | python3 -c "import sys,json; [json.loads(l) for l in sys.stdin]"
# คาดหวัง: ไม่มี error = ทุกบรรทัดเป็น valid JSON

# ตรวจ Sentry (ถ้ามี DSN)
SENTRY_DSN=https://... uvicorn app.main:app
# ดู log: "Sentry initialized"
2. Metrics Collection
เก็บ metrics ด้วย Prometheus + Grafana: request rate, error rate, latency
P3Partial

คืออะไร

Metrics คือ numeric measurements ที่เก็บตามเวลา เช่น request per second, error rate %, DB query duration (p50/p95/p99) Prometheus scrape metrics จาก app endpoint (/metrics) ทุก 15s แล้วเก็บใน time-series DB Grafana ทำ visualization

ทำไมถึงสำคัญ

Log บอกว่า "อะไรผิดพลาด" แต่ metrics บอกว่า "ระบบ healthy ไหม" เช่น error rate พุ่งจาก 0.1% เป็น 5% หลัง deploy ใหม่ — ตรวจพบได้ทันทีจาก dashboard โดยไม่ต้อง grep log

สถานะในโปรเจกต์ — บางส่วน

มีแล้ว: GET /metrics ✓ — prometheus-fastapi-instrumentator expose request count, latency histogram (p50/p95/p99), in-progress requests โดยอัตโนมัติ · main.py

ยังไม่มี: Prometheus server scraping · Grafana dashboard — ต้องการ infrastructure แยก

สถานะ — เลื่อนไปก่อน (Intentional Defer)

Prometheus server + Grafana ต้องการ infrastructure deployment ยังไม่มี production server · ทบทวนเมื่อ deploy จริงหรือมี requirement ต้องดู latency / error rate แบบ real-time

วิธีทดสอบ

# ตรวจ /metrics endpoint
uvicorn app.main:app --reload &
curl -s http://localhost:8000/health  # สร้าง traffic ก่อน
curl -s http://localhost:8000/metrics | head -30
# คาดหวัง: ได้ Prometheus text format
# http_requests_total{...} 1.0
# http_request_duration_seconds_bucket{...} ...

# ตรวจ metric เพิ่มขึ้นหลัง request
curl -s http://localhost:8000/api/v1/finance -H "Authorization: Bearer $TOKEN"
curl -s http://localhost:8000/metrics | grep http_requests_total

# ตรวจ Prometheus scrape (ถ้ามี Prometheus server)
# เพิ่มใน prometheus.yml:
# scrape_configs:
#   - job_name: finance-dashboard
#     static_configs:
#       - targets: ['localhost:8000']
#     scrape_interval: 15s
3. Distributed Tracing
ใช้ OpenTelemetry + Jaeger trace request ข้าม service
P3Defer

คืออะไร

Distributed tracing ติดตาม request ตลอด lifecycle: HTTP request → auth check → cache lookup → DB query → response แต่ละ step (span) มี duration ทำให้รู้ว่าขั้นตอนไหนเป็น bottleneck Jaeger/Zipkin เป็น UI แสดง trace

ทำไมถึงสำคัญ

เมื่อ request ช้าแบบไม่รู้ว่าเพราะอะไร tracing บอกได้ทันทีว่า 80% ของเวลาหายไปที่ DB query ไหน ทำให้ debug performance issue ได้เร็วกว่า log มาก

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

ยังเป็น single service ดังนั้นยังไม่จำเป็นเร่งด่วน · Jaeger instance ต้องการ infrastructure แยก · ทบทวนเมื่อแยก service หรือพบ performance issue ที่ log ไม่เพียงพอ debug

แผนการ implement เมื่อพร้อม

  • เพิ่ม opentelemetry-instrumentation-fastapi + opentelemetry-instrumentation-psycopg + opentelemetry-exporter-jaeger
  • ตั้ง Jaeger exporter ใน main.py: ส่ง trace ไปยัง Jaeger instance ทุก request
  • ทุก DB query และ Redis call จะ auto-instrumented ได้ทันที
  • เพิ่ม custom span สำหรับ business logic เช่น with tracer.start_as_current_span("finance.query"):

วิธีทดสอบ (เมื่อ implement แล้ว)

# รัน Jaeger ด้วย Docker
docker run -d --name jaeger -p 16686:16686 -p 6831:6831/udp jaegertracing/all-in-one

# รัน app พร้อม tracing
OTEL_EXPORTER_JAEGER_AGENT_HOST=localhost uvicorn app.main:app --reload

# สร้าง request
curl -s http://localhost:8000/api/v1/finance -H "Authorization: Bearer $TOKEN"

# ดู trace ใน Jaeger UI
open http://localhost:16686
# Search service: finance-dashboard → ดู spans ของ DB query และ Redis

# ตรวจ span duration breakdown
# HTTP request span → auth span → DB query span → response
# ดูว่า step ไหนใช้เวลามากที่สุด
4. Alerting Rules
กำหนด alert เมื่อ error rate > 1%, latency p99 > 2s, disk > 80%
P3Defer

คืออะไร

Alerting rules คือ condition ที่เมื่อ metric เกิน threshold จะส่ง notification ไปยัง on-call engineer เช่น Slack, PagerDuty, email เช่น ถ้า error rate > 1% ใน 5 นาทีที่ผ่านมา → alert ทันที

ทำไมถึงสำคัญ

ถ้าไม่มี alert engineer จะไม่รู้ว่าระบบมีปัญหาจนกว่า user จะโทรมาแจ้ง alert ทำให้ Mean Time to Detect (MTTD) ลดจากชั่วโมงเหลือนาที ส่งผลโดยตรงต่อ uptime SLO

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

ต้องการ Prometheus AlertManager ซึ่งเป็น infrastructure แยก · /metrics endpoint พร้อมแล้ว แต่ยังไม่มี Prometheus server ที่จะ scrape · ทบทวนเมื่อ deploy Prometheus + Grafana จริง

แผนการ implement เมื่อพร้อม

  • ตั้ง Prometheus AlertManager rules: error_rate > 1%, p99_latency > 2s, disk_usage > 80%
  • Integrate กับ Slack webhook หรือ Line Notify สำหรับ alert notification
  • กำหนด on-call rotation และ escalation policy

วิธีทดสอบ (เมื่อ implement แล้ว)

# ตั้ง AlertManager rule ตัวอย่าง (alertmanager.yml)
groups:
  - name: finance-dashboard
    rules:
      - alert: HighErrorRate
        expr: rate(http_requests_total{status=~"5.."}[5m]) > 0.01
        for: 2m
        annotations:
          summary: "Error rate {{ $value | humanizePercentage }}"

# ทดสอบ alert ด้วยการ trigger error จริง
for i in $(seq 1 20); do
  curl -s http://localhost:8000/api/v1/nonexistent
done
# ดู AlertManager UI: http://localhost:9093 → alert ควร fire หลัง 2 นาที

# ทดสอบ Slack notification
curl -X POST $SLACK_WEBHOOK_URL \
  -H "Content-Type: application/json" \
  -d '{"text":"Test alert from finance-dashboard"}'
5. SLI / SLO Definition
กำหนด uptime target 99.9%, p95 latency < 500ms สำหรับ API หลัก
P3Defer

คืออะไร

SLI (Service Level Indicator): metric ที่วัดได้จริง เช่น % request ที่ตอบภายใน 500ms SLO (Service Level Objective): target ที่ต้องการ เช่น 99.9% uptime SLA: commitment ต่อ customer (มี penalty ถ้าไม่ได้) SLI+SLO เป็น internal target

ทำไมถึงสำคัญ

ถ้าไม่มี SLO ทีมไม่รู้ว่า "ดีพอ" คืออะไร SLO ทำให้ตัดสินใจได้ว่าเมื่อไรต้องหยุด feature และไป fix reliability และเป็น baseline ที่วัดผลได้ว่า system ดีขึ้นหรือแย่ลงหลัง change

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

SLI/SLO ถูก define แล้ว (ดูด้านล่าง) แต่ยังวัดไม่ได้จริงเพราะยังไม่มี Prometheus server · ทบทวนเมื่อ Metrics Collection พร้อม

SLIวิธีวัดSLO Target
Availabilitysuccessful_requests / total_requests≥ 99.9% (43.8 min downtime/month)
Latency% requests ที่ตอบภายใน 500msp95 < 500ms
Error Budget1 - Availability SLO0.1% = 43.8 min/month

วิธีทดสอบ (เมื่อ Prometheus พร้อม)

# PromQL สำหรับวัด SLI จริง
# Availability SLI — % requests ที่ไม่ใช่ 5xx ใน 30 วัน
1 - (
  sum(rate(http_requests_total{status=~"5.."}[30d]))
  /
  sum(rate(http_requests_total[30d]))
)

# Latency SLI — % requests ที่เร็วกว่า 500ms
sum(rate(http_request_duration_seconds_bucket{le="0.5"}[30d]))
/
sum(rate(http_request_duration_seconds_count[30d]))

# ตรวจ error budget คงเหลือ
# ถ้า Availability SLI = 99.95% และ SLO = 99.9%
# → ใช้ error budget ไป 50% แล้ว → ควร review

# ดูว่า SLI ผ่าน SLO หรือไม่ และปรับ target ตาม reality
