1. PostgreSQL (SSH/Direct)
รองรับการเชื่อมต่อทั้งแบบ SSH tunnel และ direct connection
P1Pass

คืออะไร

รองรับการเชื่อมต่อ PostgreSQL ได้ 2 วิธี: Direct เชื่อมตรงผ่าน network, SSH Tunnel เชื่อมผ่าน SSH jump server ก่อนแล้วค่อย forward ไปยัง DB ซึ่งอยู่ใน private network ที่ไม่ expose internet โดยตรง

ทำไมถึงสำคัญ

Production DB มักอยู่ใน private network ที่เข้าถึงได้ผ่าน SSH เท่านั้น เพื่อความปลอดภัย การที่ app รองรับทั้งสองแบบทำให้ dev ใช้ direct ได้ง่าย ส่วน prod ใช้ SSH ได้ตาม network policy

สถานะในโปรเจกต์ ✓

DB_MODE=ssh|direct ใน .env · SSH ผ่าน sshtunnel + paramiko รองรับ key-based และ password auth · database.py:19-67

วิธีทดสอบ

# Direct mode — ตรวจการเชื่อมต่อ
DB_MODE=direct uvicorn app.main:app --reload
# ดู startup log: "DB pool ready"

# SSH mode — ตรวจ tunnel
DB_MODE=ssh uvicorn app.main:app --reload
# ดู startup log: "SSH tunnel established" ก่อน "DB pool ready"

# ทดสอบ health และ readiness หลัง connect
curl -s http://localhost:8000/health
# คาดหวัง: {"status": "ok", "version": "..."}

curl -s http://localhost:8000/ready
# คาดหวัง: {"status": "ok"} — ยืนยันว่า DB connect ได้จริง

ถ้า DB connect ไม่ได้ app จะ crash ที่ startup พร้อม error message — ไม่ให้ start แบบ silent failure

2. Database Indexing
ทำ index บน column ที่ใช้ filter/join บ่อย
P1Pass

คืออะไร

Database index คือโครงสร้างข้อมูลเพิ่มเติมที่ทำให้ DB ค้นหาแถวที่ต้องการได้เร็วขึ้นมาก แทนที่จะ scan ทุกแถว (sequential scan) ใช้ B-tree index ค้นได้ใน O(log n) ซึ่งแตกต่างมากเมื่อมีหลายล้านแถว

ทำไมถึงสำคัญ

Finance query ของ system นี้ทำ JOIN หลาย table และ WHERE ด้วย fiscal_year, cost_owner, gl_id ทุก query ถ้าไม่มี index แต่ละ query อาจใช้เวลาหลายวินาทีแทนที่จะเป็น milliseconds

สถานะในโปรเจกต์ ✓

migrations/004_create_indexes.sql มี 14 indexes ครอบคลุม: fiscal_year, fiscal_year+fiscal_month, year+month, gl_id, cost_ctr_id, cost_owner, IO fields (partial indexes สำหรับ nullable columns), master table PKs

วิธีทดสอบ

-- ตรวจสอบ indexes ที่มีอยู่ใน DB
SELECT indexname, tablename, indexdef
FROM pg_indexes
WHERE tablename IN ('erp_transactions', 'finance_coordinator', 'audit_log')
ORDER BY tablename, indexname;

-- ตรวจว่า query ใช้ index จริง (ต้องเห็น "Index Scan" ไม่ใช่ "Seq Scan")
EXPLAIN (ANALYZE, FORMAT TEXT)
SELECT * FROM erp_transactions
WHERE fiscal_year = 2025
LIMIT 10;
-- คาดหวัง: "Index Scan using idx_erp_fiscal_year"
3. Data Integrity
ใช้ DB constraint (NOT NULL, FK, CHECK) และจัดการ transaction ด้วย ACID
P1Pass

คืออะไร

Data integrity คือการรับประกันว่าข้อมูลใน DB ถูกต้องและสอดคล้องกันเสมอ ทำได้ด้วย constraint (NOT NULL, UNIQUE, FK, CHECK) และ ACID transaction (Atomicity, Consistency, Isolation, Durability)

ทำไมถึงสำคัญ

ถ้าไม่มี constraint อาจมี coordinator record ที่ username เป็น NULL, หรือ ERP record ที่ amount เป็น NULL ซึ่งทำให้ aggregate calculation ผิด ข้อมูลการเงินผิดพลาดสร้างความเสียหายทางธุรกิจ

สถานะในโปรเจกต์ ✓

Coordinator table: NOT NULL ทุก required field, UNIQUE(username), DEFAULT TRUE · ERP table: implicit NOT NULL ผ่าน data import · psycopg3 transaction: auto rollback เมื่อ exception ใน async with get_db()

วิธีทดสอบ

-- ทดสอบ UNIQUE constraint — insert ซ้ำต้องได้ error
INSERT INTO finance_coordinator (username, active, created_by)
VALUES ('existing@example.com', TRUE, 'admin');
-- ครั้งที่ 2 ต้องได้: ERROR: duplicate key value violates unique constraint

-- ทดสอบ NOT NULL — ส่ง username เป็น null ผ่าน API
curl -s -X POST http://localhost:8000/api/v1/admin/coordinators \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username": null}'
# คาดหวัง: 422 Unprocessable Entity (Pydantic rejects null before DB)
4. Redis Caching
Cache ข้อมูลที่เรียกบ่อย พร้อมกำหนด TTL ที่เหมาะสม
P1Pass

คืออะไร

Redis คือ in-memory data store ที่ใช้เป็น cache layer ระหว่าง application และ database ข้อมูลที่ query บ่อยและเปลี่ยนแปลงไม่บ่อยจะถูกเก็บใน Redis ซึ่งเร็วกว่า DB หลายร้อยเท่า TTL (Time To Live) กำหนดว่า cache หมดอายุเมื่อไร

ทำไมถึงสำคัญ

Finance SQL ของ system นี้ซับซ้อนมาก (CTE + หลาย JSONB_AGG) ถ้าทุก request query DB จะช้าและ DB รับ load สูง Redis cache ทำให้ request ที่ 2 เป็นต้นไปตอบได้ใน milliseconds และ DB ทำงานน้อยลงมาก

สถานะในโปรเจกต์ ✓

Finance/Budget/IO: TTL 300s (5 min) · Coordinator lookup: TTL 600s (10 min) · cache key: seamless:v1:{prefix}:{role}:{params_hash} · graceful fallback เมื่อ Redis ไม่พร้อม — app ทำงานต่อได้โดยไม่มี cache

วิธีทดสอบ

# ทดสอบ cache hit — เรียก 2 ครั้ง ดู response time
time curl -s "http://localhost:8000/api/v1/finance?year=2025" \
  -H "Authorization: Bearer $TOKEN" > /dev/null
# ครั้งแรก: ~200-500ms (DB query)

time curl -s "http://localhost:8000/api/v1/finance?year=2025" \
  -H "Authorization: Bearer $TOKEN" > /dev/null
# ครั้งที่ 2: <20ms (cache hit)

# ตรวจ cache key ใน Redis
redis-cli KEYS "seamless:v1:finance:*"
redis-cli TTL "seamless:v1:finance:fa:<hash>"
# คาดหวัง: TTL ไม่เกิน 300 วินาที

# ทดสอบ graceful fallback — หยุด Redis แล้วเรียก API
brew services stop redis
curl -s "http://localhost:8000/api/v1/finance?year=2025" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "
import sys,json; r=json.load(sys.stdin); print('success:', r.get('success'))
"
# คาดหวัง: ยังได้ data (fallback ไป DB โดยตรง)
brew services start redis
5. Connection Pooling
ใช้ connection pool ป้องกัน DB connection exhaustion
P1Pass

คืออะไร

Connection pool คือ pool ของ DB connection ที่สร้างไว้ล่วงหน้า แทนที่จะสร้าง connection ใหม่ทุก request (ซึ่งช้า) app หยิบ connection จาก pool มาใช้แล้วคืนกลับ ป้องกัน DB รับ connection เกิน limit

ทำไมถึงสำคัญ

PostgreSQL รองรับ connection จำนวนจำกัด (default 100) ถ้า app สร้าง connection ใหม่ทุก request ภายใต้ traffic สูงจะ exhaust limit ทำให้ DB reject connection ใหม่ทั้งหมด

สถานะในโปรเจกต์ ✓

psycopg3 AsyncConnectionPool min=2, max=20 · ปรับได้ผ่าน DB_POOL_MIN_SIZE, DB_POOL_MAX_SIZE · database.py:55-62 · async — ไม่ block event loop ขณะรอ connection

วิธีทดสอบ

# ส่ง concurrent request 10 ตัวพร้อมกัน — pool ต้องจัดการได้
for i in {1..10}; do
  curl -s "http://localhost:8000/api/v1/finance?year=2025" \
    -H "Authorization: Bearer $TOKEN" -o /dev/null &
done
wait
echo "All 10 requests done"

# ตรวจ log ว่าไม่มี "pool exhausted" error
tail -20 logs/app.log | grep -i "pool\|connection"

ถ้ามี error PoolTimeout ใน log แสดงว่า DB_POOL_MAX_SIZE ต้องเพิ่ม

6. Read Replica
แยก read traffic ไปยัง PostgreSQL read replica เพื่อลดภาระ primary DB
P3Defer

คืออะไร

Read replica คือ PostgreSQL instance ที่ sync ข้อมูลจาก primary แบบ real-time (streaming replication) สำหรับ read-only query เท่านั้น ทำให้ primary DB รับเฉพาะ write operation ลด load ได้มาก

ทำไมถึงสำคัญ

Finance dashboard มีเฉพาะ read query (SELECT) เกือบทั้งหมด ถ้า concurrent users มากขึ้นจน primary DB เริ่ม overload read replica จะช่วยกระจาย load ได้โดยไม่ต้องเปลี่ยน code มาก

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

ยังไม่ได้ deploy · ผู้ใช้งานไม่มาก · Redis cache (TTL 300s) ช่วยลด read load ได้เพียงพอสำหรับ load ปัจจุบัน — ทบทวนเมื่อ concurrent users สูงขึ้นจริงหรือมี cache miss บ่อย

เมื่อถึงเวลา (trigger: DB load สูง / cache miss บ่อย)

  • ตั้ง PostgreSQL streaming replication: primary → replica
  • เพิ่ม READ_REPLICA_HOST ใน config (ค่า default = primary host ถ้ายังไม่มี replica)
  • เพิ่ม get_read_db() ใน database.py ที่ fallback ไป primary pool อัตโนมัติ
  • Route Finance/IO/Budget queries ไปยัง get_read_db()
7. Database Migration
จัดการ schema migration แบบ version-controlled พร้อม rollback
P2Pass

คืออะไร

Database migration คือกระบวนการเปลี่ยน DB schema อย่างมีระเบียบผ่าน versioned files เช่น 001_create_tables.sql ที่รัน up (apply) ตามลำดับ และมี down (rollback) เพื่อย้อนกลับได้เมื่อ deploy มีปัญหา

ทำไมถึงสำคัญ

ถ้าแก้ DB โดยตรงโดยไม่มี migration file ทีม dev จะไม่รู้ว่า production DB มี schema อะไรบ้าง เมื่อ deploy ใหม่ DB จะไม่ match code ทำให้ error · หาก deploy ใหม่มีปัญหา การ rollback schema ต้องทำแบบ manual และ error-prone

สถานะในโปรเจกต์ ✓

มี custom migrations/migrate.py + 4 SQL files (001–004) ✓ — apply ตาม filename order · idempotent ผ่าน schema_migrations table · transaction per file (auto-rollback on error) · รองรับ SSH tunnel mode

Down migration ✓ — python migrate.py --rollback parse -- DOWN: block จากทุก SQL file และ execute ในลำดับย้อนกลับ (004→001) พร้อมลบ record ออกจาก schema_migrations อัตโนมัติ

วิธีทดสอบ

cd backend

# รัน migration (idempotent — รันซ้ำได้โดยไม่มีผลข้างเคียง)
python migrations/migrate.py
# คาดหวัง: "Applied: 001_create_tables.sql" ... "All migrations up to date"

# รันซ้ำ — ต้องข้ามทุกไฟล์ที่ apply แล้ว
python migrations/migrate.py
# คาดหวัง: "All migrations up to date" (ไม่มี re-apply)

# ตรวจ schema_migrations table
psql $DATABASE_URL -c "SELECT * FROM schema_migrations ORDER BY applied_at;"

# ทดสอบ rollback (ระวัง: ลบ table ทั้งหมด — ทดสอบบน test DB เท่านั้น)
python migrations/migrate.py --rollback
# คาดหวัง: rollback 004→001 ในลำดับย้อนกลับ
8. Soft Delete
ใช้ active flag แทน hard delete เพื่อรักษา data และ audit trail
P2Pass

คืออะไร

Soft delete คือการ "ลบ" ข้อมูลโดยการ set flag (active=false หรือ is_deleted=true) แทนการลบ row จริง ข้อมูลยังอยู่ใน DB สามารถ restore ได้ ตรงข้ามกับ hard delete ที่ DELETE FROM table โดยตรง

ทำไมถึงสำคัญ

สำหรับ financial data การลบข้อมูลถาวรเป็น risk ถ้า hard delete ผิดพลาดจะกู้คืนไม่ได้ soft delete ยังรักษา audit trail ว่าเคยมีรายการนี้อยู่ และสามารถ restore ได้เมื่อ admin ต้องการ

สถานะในโปรเจกต์ ✓

finance_coordinator: ใช้ active BOOLEAN DEFAULT TRUE — ไม่มี DELETE ใดๆ ในระบบ ทุก "ลบ" คือ toggle active = NOT active · PATCH /coordinators/{id} · coordinator_service.py:106

การ enforce ครอบคลุม 3 ระดับ: Auth (WHERE active = TRUE ใน login check · auth_service.py:53) · API list (?active=true/false filter · coordinator_service.py:37) · Activate endpoint (SET active = TRUE สำหรับ restore · coordinator_service.py:85)

ERP / master tables (erp_transactions, master_*): read-only import จาก ERP system — ไม่มี user-initiated delete ดังนั้นไม่ apply

วิธีทดสอบ

# 1. ดู list coordinator ทั้งหมด (active=true)
curl -s "http://localhost:8000/api/v1/admin/coordinators?active=true" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "
import sys,json; r=json.load(sys.stdin)
print('active coordinators:', r.get('total'))
"

# 2. Deactivate (soft delete) coordinator
COORD_ID=1
curl -s -X PATCH "http://localhost:8000/api/v1/admin/coordinators/$COORD_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"active": false}'

# 3. ยืนยันว่ายังอยู่ใน DB (ไม่ถูก hard delete)
curl -s "http://localhost:8000/api/v1/admin/coordinators?active=false" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "
import sys,json; r=json.load(sys.stdin)
print('inactive coordinators:', r.get('total'))
"

# 4. Restore — activate กลับ
curl -s -X PATCH "http://localhost:8000/api/v1/admin/coordinators/$COORD_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"active": true}'
9. Database Backup
ทำ full backup รายวัน + incremental รายชั่วโมง + PITR รองรับย้อนหลัง 30 วัน
P2Defer

คืออะไร

Full backup คือ snapshot ทั้ง database ณ เวลาหนึ่ง Incremental backup คือ backup เฉพาะ changes หลัง backup ครั้งล่าสุด PITR (Point-in-Time Recovery) คือความสามารถ restore DB ไปยังช่วงเวลาใดก็ได้ในอดีต

ทำไมถึงสำคัญ

ถ้า DB crash, hardware failure, หรือ ransomware — ถ้าไม่มี backup ข้อมูลการเงินทั้งหมดหาย PITR ช่วยให้ restore ได้ถึง 1 นาทีก่อนเกิดปัญหา แทนที่จะต้องย้อนไปถึง full backup ล่าสุด

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

ข้อมูลหลัก (erp_transactions, master_*) มาจาก ERP system ซึ่งเป็น source of truth — หาก local DB หายสามารถ re-import ได้ · finance_coordinator เป็นข้อมูลเล็กน้อย (user-managed) · ความเสี่ยงต่ำกว่า use case ทั่วไปที่ DB คือแหล่งข้อมูลเดียว — ทบทวนเมื่อมีข้อมูลที่ไม่ได้มาจาก ERP เพิ่มขึ้น หรือเมื่อ RTO/RPO requirement ถูกกำหนด

เมื่อถึงเวลา (trigger: มีข้อมูลนอก ERP / กำหนด RTO-RPO)

  • ตั้ง pg_dump cron job: full backup รายวัน (เก็บ 30 วัน), incremental ด้วย WAL archiving รายชั่วโมง
  • เก็บ backup ใน object storage แยก server (S3, Azure Blob) ไม่เก็บบน DB server เดียวกัน
  • Enable PostgreSQL WAL archiving สำหรับ PITR
  • ทดสอบ restore ทุก quarter เพื่อยืนยันว่า backup ใช้งานได้จริง
10. Data Retention Policy
กำหนด policy ว่าข้อมูลแต่ละประเภทเก็บนานเท่าไร ก่อน archive หรือ purge
P3Defer

คืออะไร

Data retention policy คือ rule ที่กำหนดว่าข้อมูลแต่ละประเภทต้องเก็บอย่างน้อยกี่ปี และเมื่อครบกำหนดต้องทำอะไร (archive ลง cold storage, anonymize, หรือ delete) เพื่อสมดุลระหว่าง compliance requirement และ storage cost

ทำไมถึงสำคัญ

ข้อมูลการเงินในไทยต้องเก็บตามกฎหมายบัญชีอย่างน้อย 5 ปี ถ้าเก็บมากเกินไปก็เปลืองพื้นที่และเพิ่มความเสี่ยง ถ้าเก็บน้อยเกินไปก็ผิด compliance

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

ERP data (erp_transactions): compliance retention จัดการโดย ERP upstream · local DB เป็น read mirror · ปัจจุบันมีเฉพาะ fiscal_year 2025 — ตารางโตขึ้นทุกปีที่ import แต่ยังไม่ถึงขนาดที่ต้อง archive · multi-year strategy ตัดสินใจแล้วผ่าน migration 005 (erp_transactions) · ถ้า ERP purge ข้อมูลเก่า local DB จะยังคงข้อมูลนั้นไว้ — ถือว่า acceptable สำหรับ financial data ที่ compliance กำหนด minimum retention ไม่ใช่ maximum

Master tables (master_*): reference data ที่ overwrite จาก ERP ทุกครั้งที่ import — ไม่มี retention concern

Coordinator data (finance_coordinator): มี updated_at column ที่ track เวลา deactivate · dataset เล็กในปัจจุบัน · หมายเหตุ PDPA: username เป็น personal data — inactive records ควรมีกำหนด purge ชัดเจน แม้ยังไม่ urgent ในขนาดปัจจุบัน

ทบทวนเมื่อ: มี compliance audit · erp_transactions โตเกิน storage budget · มี PDPA audit

เมื่อถึงเวลา (trigger: compliance audit / PDPA audit / data growth)

  • กำหนด retention period อย่างเป็นทางการ: ERP data 5–7 ปี (กฎหมายบัญชี) · coordinator records 2 ปีหลัง active = FALSE
  • Archive erp_transactions แยก fiscal_year ที่เกิน retention → cold storage แล้ว DELETE ออกจาก DB
    DELETE FROM erp_transactions WHERE fiscal_year < EXTRACT(YEAR FROM NOW()) - 7;
  • Purge coordinator records ที่ inactive เกินกำหนด (PDPA)
    DELETE FROM finance_coordinator WHERE active = FALSE AND updated_at < NOW() - INTERVAL '2 years';
