1. ETL / Data Import Process
กระบวนการ import ข้อมูลจาก ERP ไปยัง PostgreSQL มี error handling และ retry mechanism
P2Partial

คืออะไร

ETL (Extract, Transform, Load) คือกระบวนการ: (1) Extract ดึงข้อมูลจาก ERP source (2) Transform แปลง format, clean, validate (3) Load บันทึกลง PostgreSQL table erp_transactions กระบวนการนี้ควรมี scheduled run, error handling, และ idempotent (run ซ้ำได้โดยไม่ duplicate)

ทำไมถึงสำคัญ

Finance dashboard แสดงข้อมูลจาก ERP ถ้ากระบวนการ import ไม่ reliable ข้อมูลที่แสดงจะไม่ครบหรือผิดพลาด ผู้บริหารตัดสินใจบนข้อมูลเก่าหรือผิด ซึ่งส่งผลกระทบต่อการเงินองค์กร

สถานะในโปรเจกต์ — Partial

ETL script: etl/import_erp.py พร้อมใช้งาน:

  • Idempotent: DELETE rows ของ fiscal_year ก่อน INSERT ใหม่ — run ซ้ำได้ปลอดภัย
  • Validation: ใช้ Pydantic schema จาก etl/schemas.py — collect errors ทุก row ก่อน insert
  • Dry-run mode: --dry-run flag validate เท่านั้น ไม่แตะ DB
  • SSH Tunnel: รองรับ DB_MODE=ssh ผ่าน .env เดิม
  • Summary report: แสดง rows read / valid / rejected + 10 error rows แรก

Partial เพราะ: column mapping ใน _CSV_MAP ต้องปรับให้ตรงกับ ERP export จริง · ยังไม่มี scheduled run (Celery defer) · ยังไม่มี data freshness indicator ใน dashboard

วิธีทดสอบ

# 1. ทดสอบ validation โดยไม่แตะ DB (dry-run)
cd backend
python etl/import_erp.py --file sample_export.csv --year 2025 --dry-run
# คาดหวัง:
#   Rows read:     N
#   Valid rows:    N
#   Rejected rows: 0
#   [DRY-RUN] Done: N rows loaded

# 2. ทดสอบ validation schema โดยตรง
python -c "
from etl.schemas import ErpTransactionRow
from decimal import Decimal
from datetime import date
r = ErpTransactionRow(
    fiscal_year=2025, fiscal_month=1, trimester=1,
    day=15, month=10, year=2024, doc_no=12345,
    doc_date=date(2024,10,15), funds_ctr='FC001',
    cost_ctr_id='CC001', gl_id='GL001',
    gl_description='Test', amount=Decimal('1500.50'), details='test'
)
print('valid:', r.amount)

# ทดสอบ invalid fiscal_month
try:
    ErpTransactionRow(**{**r.model_dump(), 'fiscal_month': 20})
except Exception as e:
    print('invalid month caught:', 'fiscal_month' in str(e))
"

# 3. Import จริง (ต้องมี DB connection)
python etl/import_erp.py --file export_2025.csv --year 2025
# คาดหวัง: Done: N rows loaded
# ตรวจสอบผลลัพธ์
psql -d ic_finance -c "SELECT fiscal_year, COUNT(*), SUM(amount) FROM erp_transactions GROUP BY fiscal_year;"

# 4. ทดสอบ idempotency (รันซ้ำ 2 ครั้ง ต้องได้ผลเหมือนกัน)
python etl/import_erp.py --file export_2025.csv --year 2025
python etl/import_erp.py --file export_2025.csv --year 2025
psql -d ic_finance -c "SELECT COUNT(*) FROM erp_transactions WHERE fiscal_year=2025;"
# คาดหวัง: count ไม่เพิ่มขึ้นจากการรันครั้งที่ 2
2. Data Validation Rules
ตรวจสอบ data quality ก่อน import: range check, format check, referential integrity
P2Pass

คืออะไร

Data validation rules คือ rules ที่ตรวจสอบว่าข้อมูลที่จะ import เข้า DB ถูกต้องตาม business rules ได้แก่: (1) Format check: fiscal_year เป็น 4 หลัก, amount เป็น numeric (2) Range check: fiscal_month ระหว่าง 1-16 (ERP extended) (3) Referential check: cost_ctr_id, gl_id ต้องไม่ว่าง

ทำไมถึงสำคัญ

"Garbage in, garbage out" — ถ้า import ข้อมูลผิดเข้า DB แล้วค่อยมา detect ทีหลัง เสียต้นทุนมากกว่าการ validate ก่อน import นอกจากนั้น finance data ที่ผิดอาจส่งผลกระทบต่อการรายงานทางการเงิน

สถานะในโปรเจกต์ ✓

Application-level (Pydantic): etl/schemas.py — ErpTransactionRow validate ทุก row ก่อน insert:

  • fiscal_year: range 2000–2100
  • fiscal_month: range 1–16 (ERP extended periods)
  • month: range 1–12
  • gl_id, cost_ctr_id, funds_ctr: strip + non-empty check
  • amount: Decimal (reject non-numeric)
  • Nullable fields: coerce empty string → None

DB-level (PostgreSQL): erp_transactions มี NOT NULL บน required columns · migration 001 enforce schema constraints

Error collection: ETL script collect errors ทุก row (ไม่ abort row แรก) → print summary + row number + error message

วิธีทดสอบ

# ทดสอบ schema validation ด้วย pytest unit test
cd backend
.venv/bin/python -m pytest -v -k "schema or validation" 2>/dev/null || true

# ทดสอบ validation โดยตรง
python -c "
from etl.schemas import ErpTransactionRow
from decimal import Decimal; from datetime import date
base = dict(fiscal_year=2025, fiscal_month=1, trimester=1, day=1,
    month=10, year=2024, doc_no=1, doc_date=date(2024,10,1),
    funds_ctr='F', cost_ctr_id='C', gl_id='G',
    gl_description='D', amount=Decimal('100'), details='x')

# ✓ valid
r = ErpTransactionRow(**base); print('valid OK')

# ✗ fiscal_year ผิด
try: ErpTransactionRow(**{**base,'fiscal_year':1999})
except Exception as e: print('year caught:', '1999' in str(e))

# ✗ fiscal_month ผิด (>16)
try: ErpTransactionRow(**{**base,'fiscal_month':20})
except Exception as e: print('month caught:', 'fiscal_month' in str(e))

# ✗ gl_id ว่าง
try: ErpTransactionRow(**{**base,'gl_id':'  '})
except Exception as e: print('empty gl_id caught:', 'empty' in str(e))
"
# คาดหวัง: valid OK, ทุก invalid case ถูก caught
3. Reconciliation Process
ตรวจสอบความถูกต้องระหว่างข้อมูลใน dashboard กับ ERP source เป็นระยะ
P3Partial

คืออะไร

Reconciliation คือกระบวนการ cross-check ว่าข้อมูลใน PostgreSQL ตรงกับ ERP source หรือไม่ เช่น ยอดรวมใน dashboard ต้องเท่ากับยอดรวมใน ERP report ถ้า reconcile ไม่ผ่าน แสดงว่ามีปัญหาใน ETL หรือ transformation

ทำไมถึงสำคัญ

แม้จะมี ETL ที่ดี ก็ยังอาจเกิด bug ใน transformation ที่ทำให้ตัวเลขผิดโดยไม่รู้ตัว Reconciliation เป็น "double-check" ที่ catch ปัญหาเหล่านี้ ก่อนที่ผู้บริหารจะเห็นตัวเลขผิดใน dashboard

สถานะในโปรเจกต์ — Partial

Reconciliation script: etl/reconcile.py — compare aggregate SUM จาก DB กับ expected total จาก ERP:

  • ระบุ expected total โดยตรง: --expected-total 850000000.00
  • หรืออ่านจาก CSV summary: --expected-file erp_summary_2025.csv
  • Tolerance 0.01% (Decimal precision)
  • Report: expected / actual / difference / tolerance / row count
  • Exit code 1 ถ้า fail — ใช้ใน CI/CD หรือ scheduled job ได้ทันที

Partial เพราะ: ยังไม่มี scheduled run · ยังไม่มี reconciliation history table · ยังไม่มี alert (email/Line) เมื่อ fail

วิธีทดสอบ

# 1. ทดสอบ reconcile ด้วย expected total โดยตรง
cd backend
python etl/reconcile.py --year 2025 --expected-total 850000000.00
# คาดหวัง output:
# ==================================================
#   Reconciliation Report — Fiscal Year 2025
# ==================================================
#   ERP expected total :       850,000,000.00
#   Actual (DB) total  :       849,999,999.99
#   Difference         :                 0.01
#   Tolerance (0.01%)  :            85,000.00
#   Row count in DB    :               12,345
# --------------------------------------------------
#   Result: ✅ PASS

# 2. ทดสอบ fail case (expected ผิดมาก)
python etl/reconcile.py --year 2025 --expected-total 999999999999.00
# คาดหวัง: ❌ FAIL + exit code 1
echo "exit code: $?"

# 3. ทดสอบด้วย CSV summary file
# สร้าง erp_summary_2025.csv:
echo "fiscal_year,total_amount" > /tmp/erp_summary.csv
echo "2025,850000000.00"        >> /tmp/erp_summary.csv
python etl/reconcile.py --year 2025 --expected-file /tmp/erp_summary.csv

# 4. ใช้ใน post-ETL pipeline (exit code 1 = stop pipeline)
python etl/import_erp.py --file export_2025.csv --year 2025 && \
python etl/reconcile.py  --year 2025 --expected-total 850000000.00
# ถ้า reconcile fail → pipeline หยุดทันที

# 5. ตรวจ aggregate totals ใน DB โดยตรง
psql -d ic_finance -c "
  SELECT fiscal_year,
         COUNT(*)       AS row_count,
         SUM(amount)    AS total_amount
  FROM erp_transactions
  GROUP BY fiscal_year
  ORDER BY fiscal_year;"
