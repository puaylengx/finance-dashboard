CI/CD — 3 requirements   Pass 3 / Partial 0 / Defer 0 / Fail 0

Automated build, deploy pipeline, และ quality gates ที่ป้องกัน performance regression ก่อนถึง production

1. Automated Build & Deploy
push to main → build → test → deploy to CDN โดยอัตโนมัติ ไม่หยุด service
P2Pass

คืออะไร

CI/CD pipeline คือ automation ที่รัน build, test, และ deploy ทุกครั้งที่ push code เข้า branch หลัก โดยไม่ต้องทำ manual deploy ลด human error และทำให้ทุก deploy มี quality gate เดียวกัน

ทำไมถึงสำคัญ

Manual deploy มีโอกาสลืมขั้นตอน เช่น ลืมรัน build ก่อน หรือ deploy file เก่า automated pipeline บังคับให้ทุกอย่างเกิดตามลำดับที่ถูกต้องเสมอ

สถานะในโปรเจกต์ ✓

# .github/workflows/frontend-ci.yml
name: Frontend CI/CD
on:
  push:
    branches: [main]
    paths: ['frontend/**']

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run type-check
      - run: npm run test:unit
      - run: npm run build
      - name: Deploy to CDN
        run: aws s3 sync dist/ s3://seamless-frontend/ --delete

Pipeline รัน type check → unit test → build → deploy ตามลำดับ ถ้า step ใด fail ก็หยุดทันที

วิธีทดสอบ

Push commit ที่มี type error เข้า main — CI ต้อง fail ที่ step type-check และไม่ deploy ดู GitHub Actions tab เพื่อยืนยัน

2. Bundle Size Budget
กำหนด max bundle size ใน CI ถ้า exceed ให้ fail build ป้องกัน performance regression
P3Pass

คืออะไร

Bundle size budget คือ limit ที่กำหนดว่า JavaScript bundle ต้องไม่เกิน X KB ถ้าเกิน CI จะ fail ทำให้นักพัฒนารู้ทันทีว่า dependency ใหม่ที่เพิ่มเข้าไปทำให้ bundle ใหญ่เกินไป

ทำไมถึงสำคัญ

ถ้าไม่มี budget check library ขนาดใหญ่สามารถแอบเข้ามาใน bundle โดยไม่มีใครสังเกต ทำให้ LCP เพิ่มขึ้นเรื่อยๆ โดยไม่รู้สาเหตุ bundle size budget เป็น guard ที่ทำงานโดยอัตโนมัติ

สถานะในโปรเจกต์ — Pass

Implemented ใน scripts/check-bundle-size.js — Node.js script ที่อ่าน dist/assets/*.js หลัง build และตรวจ size ตาม limit ที่กำหนด exit code 1 ถ้า exceed:

 Bundle Size Budget (วัด 2026-06-23)

 Chunk                                  Size     Limit
 ────────────────────────────────────────────────────────
 charts     (ApexCharts)            1,133 kB   1,300 kB  ✓
 utils      (exceljs+dayjs)           908 kB   1,050 kB  ✓
 msalConfig (MSAL)                    201 kB     250 kB  ✓
 query      (TanStack+axios)           80 kB     150 kB  ✓
 vue-core   (vue+pinia+router)         30 kB      80 kB  ✓
 ────────────────────────────────────────────────────────
 TOTAL JS                           2,476 kB   2,800 kB  ✓

Scripts เพิ่มใน package.json:

"size":        "node scripts/check-bundle-size.js",  // check เฉยๆ (ต้อง build ก่อน)
"build:check": "npm run build && npm run size"         // build + check ในคำสั่งเดียว

Limit strategy: current measured size + 10-15% buffer — กัน regression โดยไม่ tight เกินไปจน fail ตลอด

วิธีทดสอบ

  1. รัน check ปกติ (ผ่าน): 
    cd frontend
npm run build:check
# ต้องเห็น: ✓ All bundle sizes within budget.
  2. จำลอง exceed limit — แก้ไข scripts/check-bundle-size.js ชั่วคราว ลด limit ให้ต่ำกว่า current size แล้วรัน: 
    npm run size
# ต้องเห็น: ✗ FAIL และ exit code 1
echo $?   # ต้องได้ 1
  3. ตรวจว่า fail จริงใน shell chain: 
    npm run size && echo "PASS" || echo "BLOCKED"
# ถ้า exceed limit → พิมพ์ "BLOCKED" (ใช้แทน CI fail ได้)
  4. ดู composition ด้วย visualizer (optional): 
    npx vite-bundle-visualizer
# เปิด stats.html เพื่อดู treemap ว่า package ไหนใหญ่

⚠ เพิ่มใน CI workflow ด้วย - run: npm run size หลัง npm run build — ถ้า exceed จะ fail pipeline ทันที

3. Lighthouse CI
วัด Core Web Vitals ทุก deploy ถ้าคะแนนต่ำกว่า threshold ให้ fail
P3Pass

คืออะไร

Lighthouse CI (LHCI) คือ automated tool ที่รัน Google Lighthouse ใน CI pipeline วัด Performance, Accessibility, Best Practices, SEO score และ Core Web Vitals ทุก deploy ถ้าคะแนนต่ำกว่า threshold ที่กำหนด CI จะ fail

ทำไมถึงสำคัญ

Core Web Vitals อาจ degrade ทีละนิดโดยไม่มีใครสังเกต LHCI จับการ degrade ระหว่าง deploy ทำให้ทีมรู้ทันทีว่า PR ใดทำให้ performance แย่ลง แทนที่จะรู้ทีหลังเมื่อ user report

สถานะในโปรเจกต์ — Pass

Implemented ด้วย @lhci/cli + .lighthouserc.json + GitHub Actions job frontend-lhci ที่รัน build → bundle check → Lighthouse ทุก push

ไฟล์ที่เพิ่ม/แก้ไข:

  • frontend/.lighthouserc.json — config: audit /login, thresholds, upload ผลไป temporary-public-storage
  • .github/workflows/ci.yml — เพิ่ม job frontend-lhci
  • frontend/package.json — เพิ่ม script "lhci": "lhci autorun"

Thresholds ที่กำหนด (audit หน้า /login เพราะหน้าอื่น require MSAL auth):

"categories:performance":    warn  ≥ 0.75
"categories:accessibility":  error ≥ 0.80   ← fail CI ถ้าต่ำกว่า
"categories:best-practices": warn  ≥ 0.80
"categories:seo":            off   (dashboard ไม่ต้อง SEO)
"largest-contentful-paint":  warn  ≤ 3000ms
"cumulative-layout-shift":   error ≤ 0.10   ← fail CI ถ้าเกิน
"total-blocking-time":       warn  ≤ 500ms

GitHub Actions job frontend-lhci (ใน .github/workflows/ci.yml):

steps:
  - npm ci
  - npm run build
  - npm run size          # bundle budget check
  - npm run lhci          # Lighthouse CI
    env:
      LHCI_GITHUB_APP_TOKEN: ${{ secrets.LHCI_GITHUB_APP_TOKEN }}

⚠ ตั้ง LHCI_GITHUB_APP_TOKEN ใน GitHub Secrets เพื่อให้ LHCI post comment บน PR แสดงคะแนนก่อน/หลัง (optional)

วิธีทดสอบ

  1. ตรวจ config ถูกต้อง: 
    cd frontend
npx lhci healthcheck
# ต้องเห็น: ✅ Chrome installation found · ✅ Configuration file found · Healthcheck passed!
  2. รัน Lighthouse ในเครื่อง (ต้อง build ก่อน): 
    npm run build
npm run lhci
# LHCI จะ start vite preview → audit /login → แสดง scores → upload link ไป temporary storage
  3. จำลอง fail threshold — แก้ .lighthouserc.json ชั่วคราว เปลี่ยน accessibility เป็น minScore: 1.0 แล้วรัน: 
    npm run lhci
# ต้องเห็น: ✖ accessibility score below threshold → exit code 1
  4. ตรวจ GitHub Actions — push commit แล้วดู tab Actions → job Lighthouse CI (Frontend) ต้องปรากฏและผ่าน
