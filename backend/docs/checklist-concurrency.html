Concurrency — 3 requirements   Pass 1 / Fail 2

การรองรับ concurrent users และการจัดการ race condition ใน financial data

1. Async FastAPI
ใช้ async/await ทั่วทั้ง codebase รองรับ concurrent request โดยไม่ block event loop
P1Pass

คืออะไร

Async programming ใน Python ใช้ async/await ทำให้ thread เดียวสามารถรอ I/O (DB query, Redis, HTTP call) โดยไม่ block และ switch ไปทำ request อื่นได้ระหว่างรอ ทำให้ server เดียวรับ concurrent request ได้มากกว่า synchronous แบบ thread-per-request

ทำไมถึงสำคัญ

Finance dashboard query DB และ Redis ซึ่งมี latency ถ้าใช้ sync programming server จะ block ระหว่างรอ ทำให้ไม่สามารถรับ request อื่นได้ async ทำให้ server รับ 100 concurrent request ด้วย memory เท่ากับรับ 10 request แบบ sync

สถานะในโปรเจกต์ ✓

ทุก endpoint, service function, DB call และ Redis call ใช้ async def และ await

async def get_finance(...):          # endpoint
    return await finance_service.get_dashboard(...)  # service

async def get_dashboard(...):
    cached = await get_cached(key)    # Redis async
    async with get_db() as conn:      # DB async pool
        await cur.execute(sql, params)

วิธีทดสอบ

# ตรวจ code — ทุก function ที่เรียก I/O ต้องเป็น async
grep -rn "^def " backend/app/api/ backend/app/services/ backend/app/core/
# คาดหวัง: ไม่พบ sync "def" ที่เรียก DB หรือ Redis

# ทดสอบ concurrent requests — ต้องตอบได้พร้อมกัน
time (
  for i in {1..5}; do
    curl -s "http://localhost:8000/api/v1/finance?year=2025" \
      -H "Authorization: Bearer $TOKEN" -o /dev/null &
  done
  wait
)
# คาดหวัง: 5 requests เสร็จในเวลาใกล้เคียงกับ 1 request เดียว
# (เพราะ async ไม่ block ระหว่างรอ)

ตรวจสอบว่าไม่มี time.sleep() หรือ synchronous requests.get() ใน codebase ซึ่งจะ block event loop

2. Database Lock Strategy
กำหนด locking strategy: optimistic lock สำหรับ read-heavy, pessimistic สำหรับ financial write
P2Fail

คืออะไร

Optimistic locking: assume ไม่มี conflict — write โดยไม่ lock แต่ check version ก่อน commit ถ้า version เปลี่ยน (คนอื่น update แล้ว) → retry Pessimistic locking: lock row ก่อน read เลย (SELECT FOR UPDATE) ป้องกัน concurrent update แต่ throughput ต่ำกว่า

ทำไมถึงสำคัญ

ถ้า 2 admin toggle coordinator พร้อมกัน โดยไม่มี lock อาจเกิด race condition ที่ผลลัพธ์ขึ้นอยู่กับ timing ทำให้ active status ผิดพลาด สำหรับข้อมูลการเงิน inconsistency นี้เป็นปัญหาร้ายแรง

สถานะในโปรเจกต์ — ยังไม่มี

ไม่มี explicit locking strategy ปัจจุบัน write operation มีเฉพาะ coordinator CRUD ซึ่งมี concurrent write น้อยมากในทางปฏิบัติ แต่ไม่ได้ protected อย่างเป็นทางการ

สิ่งที่ต้องทำ

  • Coordinator toggle: เพิ่ม SELECT FOR UPDATE ก่อน update เพื่อป้องกัน concurrent toggle
  • เพิ่ม updated_at check เพื่อ detect concurrent modification (optimistic lock)
  • ถ้ามี financial write ในอนาคต: กำหนด locking strategy ตาม business requirement
3. Idempotency Keys
ทุก write API รองรับ idempotency key ป้องกัน duplicate submission จาก client retry
P2Fail

คืออะไร

Idempotency key คือ unique ID ที่ client ส่งมาพร้อม request เพื่อบอกว่า "ถ้า request นี้ถูกส่งซ้ำ ให้ถือว่าเป็น request เดิม" server เก็บผลของ request ที่ใช้ key นี้แล้ว และตอบผลเดิมโดยไม่ process ซ้ำ

ทำไมถึงสำคัญ

Network ไม่ reliable — client อาจส่ง request แล้วไม่ได้รับ response (timeout) และ retry ถ้าไม่มี idempotency key การ retry จะสร้าง resource ซ้ำ เช่น coordinator ถูก add 2 ครั้ง (แต่ UNIQUE constraint ช่วยได้กรณีนี้)

สถานะในโปรเจกต์ — ยังไม่มี

ไม่มี Idempotency-Key header support · ปัจจุบัน UNIQUE constraint บน coordinator.username ป้องกัน duplicate add ได้บางส่วน แต่ไม่ใช่ proper idempotency

สิ่งที่ต้องทำ

  • รับ Idempotency-Key: {uuid} header ใน write endpoints
  • เก็บ key → response ใน Redis ด้วย TTL 24 ชั่วโมง
  • ถ้า key ซ้ำ: ตอบ cached response แทน process ใหม่
  • สำคัญมากถ้าเพิ่ม financial write operations ในอนาคต
