1. Clean Architecture
แยก layer: Router → Service → Repository → Model อิสระจากกัน test ง่าย
P1Pass

คืออะไร

Clean Architecture คือการแบ่ง code เป็น layers ที่มีความรับผิดชอบชัดเจน: Router/Endpoint รับ HTTP request และ validate input · Service จัดการ business logic · Core จัดการ infra (DB, Redis, security) แต่ละ layer ไม่ depend ข้ามชั้น

ทำไมถึงสำคัญ

เมื่อต้องการเปลี่ยน database ก็แก้แค่ core layer โดยไม่กระทบ business logic test service layer ได้โดย mock infra layer ใหม่ developer เข้าใจ codebase ได้เร็วเพราะรู้ว่า logic อยู่ที่ไหน

สถานะในโปรเจกต์ ✓

api/v1/endpoints/ → services/ → core/ แยกชัดเจน endpoint เรียก service function เท่านั้น ไม่มี SQL ใน endpoint · service เรียก get_db() จาก core · ไม่มี circular dependency

วิธีทดสอบ

# ตรวจว่าไม่มี SQL ใน endpoint layer
grep -rn "SELECT\|INSERT\|UPDATE\|DELETE" backend/app/api/
# คาดหวัง: ไม่พบเลย

# ตรวจว่าไม่มี get_db() ใน endpoint layer โดยตรง
grep -rn "get_db\|get_redis" backend/app/api/v1/endpoints/
# คาดหวัง: ไม่พบ (infra access อยู่ใน services/ และ core/ เท่านั้น)

# ตรวจ layer separation ด้วย import graph
grep -rn "from app.services" backend/app/api/v1/endpoints/
grep -rn "from app.core" backend/app/services/
# ทั้งสองควรพบ — แสดงว่า depend ถูกทิศทาง
2. Microservices-Ready
ออกแบบให้แยก service ได้ในอนาคต
P3Partial

คืออะไร

Microservices-Ready หมายถึงออกแบบ monolith ในลักษณะที่สามารถแยกเป็น microservices ได้ในอนาคตโดยไม่ต้อง rewrite ทั้งหมด เช่น มี clear service boundaries, ไม่มี shared mutable state ระหว่าง business domain

ทำไมถึงสำคัญ

เริ่มต้นด้วย modular monolith แล้วค่อยๆ แยกออกเมื่อจำเป็นเป็น pattern ที่ดีกว่าเริ่มด้วย microservices ทันที (ซับซ้อนเกิน) boundary ที่ชัดเจนทำให้ทีมต่างกันทำงาน parallel ได้

สถานะในโปรเจกต์ — บางส่วน

ทำแล้ว ✓ Layer separation: api/ → services/ → core/ ชัดเจน · service files แยกตาม domain (auth, finance, coordinator)

ทำแล้ว ✓ Redis key namespace: seamless:v1:{domain}:{resource}:{id} ทุก key ผ่าน builder functions ใน core/cache.py

ทำแล้ว ✓ DB domain aliases: get_auth_db, get_finance_db, get_admin_db ใน core/database.py

ทำแล้ว ✓ Service contracts: __all__ ประกาศ public API ทุก service · CoordinatorRow + CoordinatorListResult TypedDict ใน coordinator_service.py · return type annotations ครบทุก public function

ยังไม่ได้ทำ: DB aliases ยังชี้ shared pool เดียวกัน · ไม่มี service mesh

3. Health Check Endpoint
GET /health และ /ready สำหรับ container orchestrator
P2Pass

คืออะไร

/health (liveness): ตรวจว่า process ยังทำงานอยู่ไหม ถ้าไม่ตอบ orchestrator จะ restart container /ready (readiness): ตรวจว่า app พร้อมรับ traffic ไหม (DB + Redis connect ได้) ถ้าไม่พร้อม orchestrator จะไม่ส่ง traffic มา

ทำไมถึงสำคัญ

Kubernetes และ Docker Swarm ใช้ health check ตัดสินใจว่าจะ restart container ไหม และจะ route traffic ไปไหม ถ้าไม่มี /ready อาจส่ง traffic ไปยัง container ที่ DB ยังไม่ connect ทำให้ request พัง

สถานะในโปรเจกต์ ✓

GET /health — ตอบ {"status":"ok","version":"..."} ไม่ว่า DB/Redis จะพังหรือไม่ (liveness เท่านั้น) · main.py:107

GET /ready — รัน SELECT 1 กับ DB และ redis.ping() จริง ถ้า service ใด fail ตอบ 503 พร้อม {"status":"unavailable","failing":["db"]} · main.py:112

livenessProbe:
  httpGet: { path: /health, port: 8000 }
readinessProbe:
  httpGet: { path: /ready, port: 8000 }

วิธีทดสอบ

# Unit / integration tests (ไม่ต้องการ DB/Redis จริง)
cd backend
.venv/bin/python -m pytest tests/integration/test_health.py -v
# คาดหวัง: 6 passed

# ทดสอบ manual — server ต้องรันอยู่
curl -s http://localhost:8000/health
# คาดหวัง: {"status":"ok","version":"1.0.0"}

curl -s http://localhost:8000/ready
# ถ้า DB + Redis OK → 200 {"status":"ok"}
# ถ้า service ใด fail → 503 {"status":"unavailable","failing":["db"]} หรือ ["redis"]
4. Graceful Shutdown
รองรับ SIGTERM: หยุดรับ request ใหม่ รอ request ปัจจุบันเสร็จ แล้วจึง shutdown
P2Pass

คืออะไร

Graceful shutdown คือกระบวนการปิด server อย่างมีระเบียบเมื่อได้รับ SIGTERM signal (เช่น เมื่อ deploy ใหม่หรือ scale down): (1) หยุดรับ request ใหม่ (2) รอ request ที่กำลัง process อยู่เสร็จ (3) ปิด DB และ Redis connection (4) จึง exit

ทำไมถึงสำคัญ

ถ้า shutdown แบบ abrupt (kill -9) request ที่กำลัง process อยู่จะพัง transaction อาจ incomplete ทำให้ข้อมูล inconsistent graceful shutdown ทำให้ zero in-flight request loss

สถานะในโปรเจกต์ ✓

FastAPI lifespan context manager ใน main.py:33-42 รับประกัน:

@asynccontextmanager
async def lifespan(app):
    await init_db(); await init_redis()  # startup
    yield
    await close_db(); await close_redis()  # shutdown

uvicorn รับ SIGTERM และรอ in-flight request เสร็จก่อน call lifespan cleanup

วิธีทดสอบ

# รัน server แล้วส่ง SIGTERM — ดู log ว่า shutdown ครบ
uvicorn app.main:app &
SERVER_PID=$!

# รอ startup
sleep 2

# ส่ง request ที่ใช้เวลานาน (background)
curl -s "http://localhost:8000/api/v1/finance?year=2025" \
  -H "Authorization: Bearer $TOKEN" &

# ส่ง SIGTERM ทันที
kill -TERM $SERVER_PID

# ดู log — ต้องเห็น sequence นี้:
# 1. "Received shutdown signal"
# 2. (รอ in-flight request เสร็จ)
# 3. "Shutdown complete"
tail -10 logs/app.log

ผลที่คาดหวัง: request ที่กำลัง process เสร็จก่อน server ปิด ไม่มี "connection closed" error

5. Background Job Queue
ใช้ Celery + Redis สำหรับ heavy task ที่ใช้เวลานาน
P3Defer

คืออะไร

Background job queue คือระบบที่รับ task และประมวลผลแบบ async โดยไม่ block HTTP request เช่น user เรียก POST /reports/generate ระบบตอบ 202 Accepted ทันที แล้ว process report ใน background worker แยกต่างหาก

ทำไมถึงสำคัญ

HTTP request มี timeout (client browser timeout ~30-60s) ถ้า task ใช้เวลานานกว่านั้น request จะ timeout แม้ว่างาน process ยังไม่เสร็จ background queue แก้ปัญหานี้และยัง retry ได้เมื่อ worker crash

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

Finance SQL ซับซ้อนแต่ยังอยู่ในระดับ ms ยังไม่มี endpoint ที่ generate PDF หรือ export Excel — ยังไม่มี use case จริงที่ต้องการ background queue · ทบทวนเมื่อมี heavy task ที่ใช้เวลา >10s หรือมี request export จาก user จริง

แผนการ implement เมื่อพร้อม

  • เพิ่ม celery[redis]>=5.4.0 ใน requirements.txt
  • สร้าง app/core/celery_app.py — Celery instance ใช้ Redis DB 1 เป็น broker + result backend (แยกจาก cache DB 0)
  • สร้าง app/tasks/report_tasks.py — task ใช้ psycopg sync API โดยตรง (ไม่ share async pool กับ FastAPI)
  • เพิ่ม POST /reports/generate → ตอบ 202 พร้อม task_id
  • เพิ่ม GET /tasks/{task_id} → ตรวจ status (PENDING/STARTED/SUCCESS/FAILURE) และดึง result
  • Deploy Celery worker เป็น process แยกจาก FastAPI server

6. Message Queue / Event Bus
พิจารณา RabbitMQ / Kafka สำหรับ decoupling service
P4Defer

คืออะไร

Message queue (RabbitMQ) หรือ event bus (Kafka) คือ middleware ที่ทำให้ services สื่อสารกันแบบ async ผ่าน message/event แทนการ call API โดยตรง ทำให้ decouple กัน — producer ไม่รู้จัก consumer

ทำไมถึงสำคัญ

เมื่อ system มีหลาย service เช่น เมื่อมีการ import ERP data → trigger notification service + audit service + cache invalidation การใช้ event bus ทำให้เพิ่ม consumer ใหม่ได้โดยไม่แก้ producer

สถานะในโปรเจกต์ — เลื่อนไปก่อน (Intentional Defer)

ยังเป็น monolith service เดียว ทุกอย่าง call function โดยตรงใน process เดียวกัน — เหมาะกับขนาดและ team ปัจจุบัน · ทบทวนเมื่อแยก service ออกจากกันจริง เช่น notification service, ERP import service, หรือเมื่อมี consumer >1 ที่ต้องรับ event เดียวกัน

แผนการ implement เมื่อพร้อม

  • เลือก broker ตาม use case: RabbitMQ สำหรับ task queue ทั่วไป, Kafka สำหรับ event stream ที่ต้องการ replay หรือ throughput สูง
  • กำหนด event schema: {"event": "erp.imported", "payload": {...}, "timestamp": "..."}
  • สร้าง producer ใน FastAPI เมื่อ data เปลี่ยน เช่น หลัง ERP import สำเร็จ
  • สร้าง consumer service แยก subscribe event → trigger cache invalidation / notification
  • เพิ่ม Dead Letter Queue (DLQ) สำหรับ message ที่ process ไม่สำเร็จ
