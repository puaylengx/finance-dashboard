Performance — 5 requirements   Pass 3 / Partial 0 / Defer 0 / Fail 2

ความเร็วและประสิทธิภาพในการโหลดและแสดงผล ครอบคลุม bundle size, runtime performance, และ network optimization

1. Code Splitting
ใช้ Vue lazy loading + dynamic import แยก chunk ตาม route ลด initial bundle size
P2Pass

คืออะไร

Code splitting คือการแบ่ง JavaScript bundle ออกเป็นหลาย chunk แทนที่จะส่ง code ทั้งหมดในครั้งเดียว browser จะโหลดเฉพาะ chunk ที่ต้องการตอนนี้ — code ของ route อื่นโหลดเมื่อ navigate ไป

ทำไมถึงสำคัญ

Initial bundle ที่ใหญ่ทำให้ LCP (Largest Contentful Paint) สูง user รอนาน financial dashboard มักมี code เยอะ (charts, tables, filters) code splitting แก้ปัญหานี้โดยตรง

สถานะในโปรเจกต์ ✓

  • Vue Router ใช้ dynamic import สำหรับทุก page component
  • Heavy components (chart, PDF export) ใช้ defineAsyncComponent
  • Vite แยก chunk อัตโนมัติตาม dynamic import — vendor chunk แยกต่างหาก
// router/index.ts — lazy loading per route
const routes = [
  {
    path: '/dashboard',
    component: () => import('@/pages/DashboardPage.vue')  // separate chunk
  },
  {
    path: '/budget',
    component: () => import('@/pages/BudgetPage.vue')
  }
]

วิธีทดสอบ

npm run build
# ดู dist/ folder — ต้องมีหลาย JS chunks
ls dist/assets/*.js | wc -l  # ควรมากกว่า 3 files

# ตรวจสอบ Network tab ใน Chrome DevTools
# เมื่อ navigate ไป /budget ครั้งแรก ต้องเห็น chunk ใหม่โหลดมา
2. CDN
ส่ง static asset ผ่าน CDN ที่ใกล้ผู้ใช้ที่สุด ลด latency
P3Pass

คืออะไร

CDN (Content Delivery Network) คือเครือข่าย server ที่กระจายอยู่ทั่วโลก เมื่อ user โหลด JS/CSS/image ระบบส่งจาก server ที่ใกล้ที่สุด แทนที่จะส่งจาก origin server ลด latency ได้มาก

ทำไมถึงสำคัญ

ถ้า origin server อยู่สิงคโปร์ แต่ user อยู่เชียงใหม่ ทุก asset ต้องเดินทาง 2,000+ km ทำให้ LCP สูง CDN ทำให้ static asset มาจาก edge node ใกล้ๆ แทน

สถานะในโปรเจกต์ ✓

  • Deploy pipeline อัปโหลด dist/ ไปยัง cloud CDN (Cloudfront / Azure CDN)
  • Asset files มี content hash ใน filename (index.a3f4b2c1.js) — cache-busting อัตโนมัติ
  • Cache-Control header: max-age=31536000, immutable สำหรับ hashed assets

วิธีทดสอบ

ใน Chrome DevTools → Network → โหลดหน้า — ดูที่ Response Headers ของ JS/CSS files ต้องเห็น x-cache: Hit from cloudfront หรือ equivalent CDN header

3. Core Web Vitals
LCP < 2.5s, FID < 100ms, CLS < 0.1 วัดด้วย Lighthouse CI ใน pipeline
P2Pass

คืออะไร

Core Web Vitals คือ 3 metrics ที่ Google กำหนดวัด user experience: LCP (Largest Contentful Paint — ความเร็วโหลด), FID (First Input Delay — ความตอบสนอง), CLS (Cumulative Layout Shift — ความเสถียรของ layout)

ทำไมถึงสำคัญ

Core Web Vitals วัด experience จริงของ user — ไม่ใช่แค่ network speed LCP สูงทำให้รู้สึกว่าระบบช้า CLS สูงทำให้ปุ่มกระโดดขณะกำลังจะกด ซึ่งเป็นอันตรายสำหรับ financial action

สถานะในโปรเจกต์ ✓

  • LCP: ตัวเลข hero ใช้ skeleton loader — ไม่มี layout shift เมื่อโหลดเสร็จ
  • CLS: กำหนด explicit width/height บน image และ chart container ป้องกัน layout shift
  • FID: ไม่มี long JS task บน main thread ระหว่าง initial load
  • Lighthouse score: Performance ≥ 90 ใน CI pipeline

วิธีทดสอบ

# รัน Lighthouse ใน terminal
npx lighthouse http://localhost:5173 --output=json --quiet \
  | python3 -c "import sys,json; r=json.load(sys.stdin)['categories']['performance']; print(f'Score: {r[\"score\"]*100:.0f}')"

# หรือใน Chrome DevTools → Lighthouse tab → Generate report

Thresholds: LCP < 2.5s · FID < 100ms · CLS < 0.1 · Performance score ≥ 90

4. Virtual Scrolling
ใช้ virtual scroll บนตารางที่มีข้อมูลเป็นหมื่นแถว ไม่ render DOM ทั้งหมด
P2Fail

คืออะไร

Virtual scrolling คือเทคนิคที่ render เฉพาะแถวที่อยู่ใน viewport ณ ขณะนั้น แม้ข้อมูลมี 50,000 แถว แต่ DOM มีแค่ ~30 node เสมอ โดยคำนวณ offset ตาม scroll position

ทำไมถึงสำคัญ

ตาราง ERP transaction อาจมีหลายหมื่นแถวต่อปี ถ้า render ทั้งหมด browser จะสร้าง DOM nodes หลายหมื่น node ทำให้ scroll ติดขัด, layout recalculation ช้า, และอาจ crash บน mobile device ที่ RAM น้อย

สถานะในโปรเจกต์ — ยังไม่มี

ปัจจุบัน DataTable render แถวทั้งหมดใน DOM ยังไม่มี virtualization

สิ่งที่ต้องทำ

Option 1 (แนะนำ): @tanstack/vue-virtual

npm install @tanstack/vue-virtual

# VirtualDataTable.vue
import { useVirtualizer } from '@tanstack/vue-virtual'

const parentRef = ref<HTMLDivElement | null>(null)
const rowVirtualizer = useVirtualizer({
  count: rows.value.length,
  getScrollElement: () => parentRef.value,
  estimateSize: () => 44,  // row height px
  overscan: 5,
})

// template: render rowVirtualizer.getVirtualItems() เท่านั้น
// ตั้ง paddingTop/paddingBottom เพื่อ simulate scroll height

Option 2: vue-virtual-scroller (ง่ายกว่าแต่ bundle ใหญ่กว่า)

npm install vue-virtual-scroller
# ใช้ <RecycleScroller :items="rows" :item-size="44"> wrapper

เมื่อใช้งาน: ตาราง ERP transactions และทุก list ที่อาจมีข้อมูลเกิน 500 แถว

⚠ Virtual scroll ใช้ไม่ได้กับ CSS position: sticky header แบบปกติ ต้องออกแบบ sticky header แยก

5. Image Optimization
ใช้ WebP format, lazy loading, และ srcset สำหรับ responsive images
P4Fail

คืออะไร

Image optimization ครอบคลุม: (1) WebP format — ขนาดเล็กกว่า JPEG 25–34%, (2) Lazy loading — โหลดรูปเมื่อเลื่อนมาถึง viewport, (3) srcset — ส่งรูปขนาดต่างกันตาม screen resolution

ทำไมถึงสำคัญ

Images คิดเป็น ~50-70% ของน้ำหนักหน้าเว็บโดยเฉลี่ย ถึงแม้ financial dashboard จะไม่มีรูปเยอะ แต่ logo, avatar, และ icon sprites ก็ควร optimize ไว้ก่อน

สถานะในโปรเจกต์ — ยังไม่มี

รูปภาพใช้ PNG/JPG ธรรมดา ไม่มี lazy loading attribute ไม่มี srcset

สิ่งที่ต้องทำ

  • เพิ่ม vite-plugin-imagemin ใน vite.config.ts — auto-convert PNG→WebP ตอน build
  • เพิ่ม loading="lazy" ทุก <img> ที่ไม่อยู่ above the fold
  • เพิ่ม srcset สำหรับรูปที่ขนาดต่างกันตาม viewport
  • ใช้ <picture> element เพื่อ fallback จาก WebP → PNG บน browser เก่า
// vite.config.ts
import viteImagemin from 'vite-plugin-imagemin'
plugins: [
  vue(),
  viteImagemin({ webp: { quality: 80 }, png: { quality: 80 } })
]

// template
<picture>
  <source srcset="logo.webp" type="image/webp" />
  <img src="logo.png" alt="Logo" loading="lazy" width="120" height="40" />
</picture>

เนื่องจาก financial dashboard ไม่ heavy on images ข้อนี้จึง P4 (Low) — ทำหลังจาก P1/P2/P3 เสร็จ
