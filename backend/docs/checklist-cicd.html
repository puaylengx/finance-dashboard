Deployment & CI/CD — 6 requirements   Pass 3 / Partial 1 / Defer 2 / Fail 0

กระบวนการ deploy, environment management และ recovery strategy

1. Docker / Container
containerize ทั้ง backend ด้วย Docker, ใช้ Docker Compose สำหรับ local dev
P2Pass

คืออะไร

Docker package application พร้อม dependencies ทั้งหมดลงใน container image ทำให้ run ได้เหมือนกันทุก environment (dev, staging, production) โดยไม่ขึ้นกับ OS หรือ Python version ที่ติดตั้งบนเครื่อง

ทำไมถึงสำคัญ

"Works on my machine" problem หมดไป — container รับประกันว่า code ที่ test บน dev จะ run แบบเดียวกันบน production ยังช่วย scale ง่าย (run หลาย container), rollback ง่าย (ย้อนกลับ image version เดิม)

สถานะในโปรเจกต์ ✓

Multi-stage Dockerfile: backend/Dockerfile — builder stage install dependencies, runtime stage copy เฉพาะ artifact (ลด image size) · built-in HEALTHCHECK ที่ /health · --workers 2

Docker Compose: docker-compose.yml ที่ project root — รวม api + redis:7-alpine พร้อม healthcheck dependency · secrets inject ผ่าน env_file ไม่ bake ใน image · logs mount ที่ backend/logs/

วิธีทดสอบ

# ต้องมี Docker Desktop รันอยู่
cd /path/to/finance-dashboard

# Build และรัน
docker compose up --build -d

# ตรวจสถานะ
docker compose ps
# คาดหวัง: api (healthy), redis (healthy)

# ทดสอบ health endpoint
curl http://localhost:8000/health
# คาดหวัง: {"status":"ok"}

# ดู logs
docker compose logs api --tail=50

# หยุด
docker compose down

# Build image เดี่ยว
docker build -t seamless-dashboard-api:v1.0.0 backend/
docker run --rm -p 8000:8000 --env-file backend/.env seamless-dashboard-api:v1.0.0
2. Environment Separation
แยก config ระหว่าง dev / staging / production ไม่ให้ config ปนกัน
P2Pass

คืออะไร

แต่ละ environment (dev, staging, prod) ควรมี config แยกกัน ได้แก่ database URL, Redis URL, JWT secret, Sentry DSN, CORS origins เป็นต้น ป้องกัน dev code connect ไปยัง production database โดยบังเอิญ

ทำไมถึงสำคัญ

Accident cross-environment เป็นหนึ่งในสาเหตุ data loss ที่พบบ่อย developer รัน test บน dev แล้วลบ record แต่ connect ไป production database โดยไม่รู้ตัว

สถานะในโปรเจกต์ ✓

  • Template: backend/.env.example อัปเดตแล้ว — มีทุก key พร้อม comment รวมถึง APP_ENV=dev|staging|production
  • Startup guard: config.py validate_production_secrets() — ถ้า APP_ENV=production และ DRAFT_MODE=true → raise ValueError ทำให้ app refuse to start
  • .gitignore: .env และ .env.* ถูก exclude แล้ว (เว้น .env.example) — ไม่มีทาง commit secret โดยไม่ตั้งใจ
  • Config file ต่อ environment: สร้าง .env.dev / .env.staging / .env.prod จาก .env.example บน server แต่ละตัว (ไม่ commit ลง git)

วิธีทดสอบ

# ทดสอบ startup guard — ต้อง fail เมื่อ production + draft_mode
APP_ENV=production DRAFT_MODE=true \
  .venv/bin/python -c "from app.core.config import settings"
# คาดหวัง: ValueError: DRAFT_MODE must be false when APP_ENV=production

# ทดสอบผ่าน
APP_ENV=production DRAFT_MODE=false DEBUG=false \
  JWT_SECRET_KEY=my-secure-secret-key \
  .venv/bin/python -c "from app.core.config import settings; print('OK')"
# คาดหวัง: OK

# ตรวจ .gitignore ครอบคลุม
git check-ignore -v backend/.env              # ควรถูก ignore
git check-ignore -v backend/.env.production   # ควรถูก ignore
git check-ignore -v backend/.env.example      # ไม่ถูก ignore (intentional)
3. CI/CD Pipeline
automated pipeline สำหรับ test → build → deploy เมื่อ push code
P2Partial

คืออะไร

CI/CD (Continuous Integration/Deployment) คือ automated pipeline ที่รัน test, build Docker image, และ deploy โดยอัตโนมัติเมื่อ push code ไป repository ตัวอย่างเช่น GitHub Actions, GitLab CI, Jenkins

ทำไมถึงสำคัญ

Manual deploy เป็นแหล่ง human error — ลืม run migration, deploy ผิด branch, ไม่ run test ก่อน CI/CD รับประกันว่าทุก deploy ผ่าน test และใช้ process เดิมเสมอ ลด risk และเพิ่มความเร็วในการ release

สถานะในโปรเจกต์ — CI ✓ / CD ยังไม่มี

CI (Continuous Integration): .github/workflows/ci.yml — รัน pytest อัตโนมัติทุก push ไป main/develop และทุก Pull Request ไป main · ใช้ pip cache เพื่อความเร็ว · inject env vars ที่จำเป็นสำหรับ tests

CD (Continuous Deployment): ยังไม่มี — ต้องการ Docker registry (GHCR/ECR) และ production server ที่กำหนด ทำเมื่อ infrastructure พร้อม

วิธีทดสอบ

# ตรวจว่า CI workflow ถูก parse ได้ถูกต้อง
# (ต้อง push ขึ้น GitHub ก่อน)
# GitHub Actions จะรัน ci.yml อัตโนมัติเมื่อ:
#   git push origin main
#   git push origin develop
#   gh pr create --base main ...

# ทดสอบ locally ด้วย act (GitHub Actions local runner)
# brew install act
act push --workflows .github/workflows/ci.yml

# ดูผล CI ใน GitHub
gh run list --workflow=ci.yml
gh run view   # ดู run ล่าสุด

# CD step ที่ต้องเพิ่มเมื่อพร้อม (ใส่หลัง test job)
# deploy:
#   needs: test
#   if: github.ref == 'refs/heads/main'
#   steps:
#     - run: docker build -t ghcr.io/org/seamless-api:${{ github.sha }} backend/
#     - run: docker push ghcr.io/org/seamless-api:${{ github.sha }}
#     - run: ssh deploy@server "docker compose pull && docker compose up -d"
4. Zero-Downtime Deployment
deploy ได้โดยไม่มี service interruption ด้วย rolling deploy หรือ blue-green
P3Defer

คืออะไร

Rolling deploy: ค่อยๆ replace container ทีละ instance โดย load balancer ยัง route traffic ไปยัง instance เก่าที่ยังทำงาน ทำให้ไม่มี downtime Blue-green: มี 2 environment (blue=current, green=new) switch traffic ทีเดียวเมื่อ green พร้อม rollback ง่ายมาก

ทำไมถึงสำคัญ

ถ้า deploy ทำให้ service down 30 วินาที users ที่กำลัง access dashboard จะเห็น error หรือ data ไม่ครบ สำหรับ financial system ที่ใช้งานระหว่างเวลาทำงาน ต้องการ high availability

Defer — ต้องมี load balancer / orchestrator ก่อน

FastAPI ของโปรเจกต์นี้ ready รองรับแล้ว โดยไม่ต้องแก้ code:

  • lifespan() ใน main.py — graceful shutdown รองรับ SIGTERM แล้ว (close DB pool + Redis)
  • /health และ /ready endpoints — load balancer ใช้เป็น health probe ได้ทันที
  • DB migrations มี -- DOWN: blocks — backward-compatible strategy ทำได้

เมื่อมี infrastructure ให้เลือก strategy:

  • Docker Compose: docker compose up --no-deps --build api (single-instance, brief downtime)
  • Docker Swarm: deploy.update_config.order: start-first → true rolling deploy
  • Kubernetes: RollingUpdate strategy พร้อม readinessProbe: /ready
  • Nginx: upstream เป็น 2 instance, deploy ทีละตัว

วิธีทดสอบ (เมื่อพร้อม)

# ตรวจ graceful shutdown — ต้องรับ SIGTERM แล้วรอ request ที่ค้างอยู่
kill -TERM $(pgrep -f "uvicorn app.main")
# คาดหวัง: log "Shutdown complete" ก่อน process exit

# ทดสอบ rolling deploy ด้วย Docker Compose (brief downtime)
docker compose up --no-deps --build -d api
# ดู: request ช่วง replace → error หรือไม่ (benchmark ด้วย wrk/hey)

# ทดสอบ readiness probe
curl http://localhost:8000/ready
# คาดหวัง: 200 {"status":"ok"} ก่อน accept traffic
5. Rollback Plan
มี documented และ tested procedure สำหรับ rollback เมื่อ deploy พัง
P2Pass

คืออะไร

Rollback plan คือ procedure ที่ชัดเจนสำหรับการย้อนกลับไปยัง version เดิมเมื่อ deploy ใหม่มีปัญหา ประกอบด้วย: วิธี rollback application, วิธี rollback DB migration (ถ้ามี), และเวลาที่ยอมรับได้ (RTO)

ทำไมถึงสำคัญ

ทุก deploy มีความเสี่ยง ถ้าไม่มี rollback plan ที่ tested ไว้ล่วงหน้า การแก้ปัญหาหลัง deploy พังจะใช้เวลานานและ stressful ในขณะที่ production down

สถานะในโปรเจกต์ ✓

DB Migration Rollback: migrations/migrate.py --rollback อ่าน -- DOWN: comment block จากทุก migration file และ run ย้อนกลับ reverse order · ทุก migration 001–007 มี DOWN block ครบถ้วน

Docker Image Rollback: Dockerfile สร้าง versioned image ด้วย git SHA tag (:${{ github.sha }} ใน CI) ทำให้ rollback ได้ทันทีด้วย docker compose up ด้วย image เก่า

Rollback Procedure (step-by-step)

# ── App Rollback ────────────────────────────────────────────
# 1. ระบุ image version ที่ต้องการ rollback ไป
docker images seamless-dashboard-api --format "{{.Tag}} {{.CreatedAt}}"

# 2. อัปเดต docker-compose.yml image tag เป็น version ก่อนหน้า
#    image: seamless-dashboard-api:<previous-sha>

# 3. Deploy image เก่า
docker compose up -d api
# คาดหวัง: container ขึ้นด้วย image เก่า

# ── DB Migration Rollback ────────────────────────────────────
# (เฉพาะเมื่อ migration ใหม่ทำให้พัง)
cd backend
python migrations/migrate.py --rollback
# ตรวจว่า rollback สำเร็จ
psql -d finance_db -c "SELECT filename, applied_at FROM schema_migrations ORDER BY id DESC LIMIT 5;"

# ── ตรวจสอบหลัง rollback ──────────────────────────────────
curl http://localhost:8000/health   # ต้อง 200
curl http://localhost:8000/ready    # ต้อง 200

ทดสอบ rollback procedure อย่างน้อยปีละ 1 ครั้งใน staging ก่อน production

6. Disaster Recovery Plan
กำหนด RTO/RPO และ procedure สำหรับกรณี server หรือ database พัง
P3Defer

คืออะไร

RTO (Recovery Time Objective): นานแค่ไหนที่ยอมรับได้ก่อน system กลับมา (เช่น 4 ชั่วโมง) RPO (Recovery Point Objective): ข้อมูลย้อนหลังไปแค่ไหนที่ยอมสูญเสียได้ (เช่น 1 ชั่วโมง = backup ทุก 1 ชั่วโมง) DR plan คือ documented procedure ว่าถ้า server พัง จะ restore ได้ภายใน RTO ด้วย data ไม่เก่ากว่า RPO

ทำไมถึงสำคัญ

ถ้าไม่มี DR plan และ server พัง team จะตื่นตกใจและ recover ไม่ได้ตาม SLA ระบบ finance ที่มี backup และ DR plan ชัดเจนสามารถ restore ได้เร็วและ predictable

Defer — ต้องมี backup infrastructure ก่อน

Prerequisite: DB automated backup (ดู Data Management checklist item 4) ต้องพร้อมก่อน DR plan จึงจะมีความหมาย

RTO/RPO เบื้องต้นที่แนะนำ (กำหนดร่วมกับ stakeholders):

  • RTO = 4 ชั่วโมง: ระบบต้องกลับมาภายใน 4h นับจากเหตุการณ์
  • RPO = 1 ชั่วโมง: ข้อมูลสูญหายได้ไม่เกิน 1h → backup ทุก 1 ชั่วโมง

DR Runbook ที่ต้องเขียน (เมื่อพร้อม):

  • App server down: restore Docker container จาก image registry + config
  • Redis down: restart container — cache miss ชั่วคราว, app ยังทำงานได้
  • DB unreachable: app return 503 อัตโนมัติ (ผ่าน /ready endpoint) — restore จาก pg_dump backup
  • SSH tunnel down: reconnect procedure + fallback config
  • ทดสอบ DR drill อย่างน้อย 2 ครั้งต่อปี ใน staging
  • เก็บ backup ที่ offsite location (S3, Backblaze, etc.)

วิธีทดสอบ (เมื่อ backup พร้อม)

# ทดสอบ DR scenario: DB unreachable
# 1. หยุด DB (หรือ block port)
# 2. ตรวจ /ready ต้อง 503
curl http://localhost:8000/ready
# คาดหวัง: 503 {"status":"unavailable","failing":["db"]}

# 3. ตรวจว่า app ยัง serve /health (liveness probe)
curl http://localhost:8000/health
# คาดหวัง: 200 {"status":"ok"}

# ทดสอบ DB restore จาก backup
pg_restore -h localhost -U postgres -d ic_finance_restored backup.dump
# ตรวจว่าข้อมูลครบ

# ทดสอบ Redis down — app ต้องยังทำงาน (ไม่มี cache แค่ช้าขึ้น)
docker compose stop redis
curl http://localhost:8000/api/v1/finance?year=2025 -H "Authorization: Bearer $TOKEN"
# คาดหวัง: 200 (cache miss, query DB โดยตรง)
