API Design — 8 requirements   Pass 8 / Partial 0 / Fail 0

ออกแบบ API ให้ถูกต้อง สม่ำเสมอ และปลอดภัย ตามมาตรฐาน REST

1. API Versioning
กำหนด version ใน URL เช่น /api/v1/ เพื่อให้อัปเกรดโดยไม่ทำลาย client เดิม
P1Pass

คืออะไร

การฝัง version number ไว้ใน URL path เช่น /api/v1/finance ทำให้สามารถออก v2 ที่มี breaking change ได้โดย client เดิมที่ใช้ v1 ยังทำงานได้ปกติ ไม่ต้อง migrate ทันที

ทำไมถึงสำคัญ

เมื่อ API เติบโตขึ้น การเปลี่ยน response format หรือ endpoint structure เป็นสิ่งหลีกเลี่ยงไม่ได้ ถ้าไม่มี versioning client ทุกตัวจะพังพร้อมกันเมื่อมี breaking change ซึ่งเป็นปัญหาใหญ่โดยเฉพาะเมื่อมี mobile app หรือ third-party integration

สถานะในโปรเจกต์ ✓

ทุก endpoint อยู่ภายใต้ /api/v1/ ผ่าน main.py:100

app.include_router(v1_router, prefix="/api/v1")

ถ้าต้องการ v2 สร้าง api/v2/router.py และ include_router ใหม่ได้ทันที โดยไม่กระทบ v1

วิธีทดสอบ

# ยืนยัน prefix /api/v1 ในทุก endpoint
curl -s http://localhost:8000/api/v1/auth/me \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# ทดสอบ path ที่ไม่มี version → ต้องได้ 404
curl -s -o /dev/null -w "%{http_code}" http://localhost:8000/auth/me
# คาดหวัง: 404

ผลที่คาดหวัง: ทุก endpoint ตอบได้เฉพาะเมื่อผ่าน prefix /api/v1/ เท่านั้น

2. RESTful + JSON
ใช้สถาปัตยกรรม RESTful ส่งข้อมูลในรูปแบบ JSON มาตรฐาน
P1Pass

คืออะไร

REST (Representational State Transfer) คือ architectural style ที่ใช้ HTTP method แทน action: GET=อ่าน, POST=สร้าง, PATCH=แก้ไขบางส่วน, DELETE=ลบ และใช้ URL แทน resource เช่น /coordinators/1 แทน /getCoordinatorById?id=1 ข้อมูลรับส่งเป็น JSON

ทำไมถึงสำคัญ

REST เป็น industry standard ที่ client ทุกประเภท (web, mobile, third-party) เข้าใจตรงกัน ความ stateless ของ REST ทำให้ scale ได้ง่าย เพราะ server ไม่ต้องจำ state ของ client

สถานะในโปรเจกต์ ✓

HTTP method ถูกต้องทุก endpoint: GET /finance, POST /coordinators, PATCH /coordinators/{id} FastAPI + Pydantic serialize/deserialize JSON อัตโนมัติ ไม่มีการ string-format response

วิธีทดสอบ

# ทดสอบ GET — อ่านข้อมูล (ต้องได้ 200)
curl -s -o /dev/null -w "%{http_code}" \
  http://localhost:8000/api/v1/auth/me \
  -H "Authorization: Bearer $TOKEN"

# ทดสอบ POST — สร้าง resource (ต้องได้ 201)
curl -s -o /dev/null -w "%{http_code}" \
  -X POST http://localhost:8000/api/v1/admin/coordinators \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username": "test.rest@example.com"}'

# ทดสอบ DELETE method ที่ไม่ใช่ allowed → ต้องได้ 405 Method Not Allowed
curl -s -o /dev/null -w "%{http_code}" \
  -X PUT http://localhost:8000/api/v1/auth/me \
  -H "Authorization: Bearer $TOKEN"
# คาดหวัง: 405

ตรวจสอบว่า response เป็น JSON เสมอ: Content-Type: application/json

3. Error Handling
ตอบ HTTP status code ที่เหมาะสม พร้อม error message ที่เข้าใจง่าย
P1Pass

คืออะไร

การตอบ HTTP status code ที่สื่อความหมายถูกต้อง เช่น 401=ยังไม่ได้ login, 403=login แล้วแต่ไม่มีสิทธิ์, 404=ไม่พบ resource, 422=ข้อมูล input ผิด format พร้อม error message ที่ developer เข้าใจได้

ทำไมถึงสำคัญ

ถ้าทุก error ตอบ 200 OK หรือ 500 หมด client จะไม่รู้ว่าเกิดอะไรขึ้น — ต้อง parse body เพื่อหา error ซึ่งซับซ้อนและเกิด bug ง่าย status code ที่ถูกต้องช่วยให้ frontend handle error ได้อัตโนมัติ

สถานะในโปรเจกต์ ✓

ครอบคลุมทุก case: 200 success, 201 created, 400 bad request, 401 unauthorized, 403 forbidden, 404 not found, 409 conflict, 422 validation (auto Pydantic), 429 rate limit, 500 internal, 503 service unavailable

Global exception handler ใน main.py:91-97 catch unhandled error และตอบ 500 พร้อม {"success": false, "error": "Internal server error"}

วิธีทดสอบ

# 401 — ไม่มี token
curl -s -o /dev/null -w "%{http_code}" http://localhost:8000/api/v1/auth/me

# 422 — ส่ง year ผิด format (Pydantic validation)
curl -s "http://localhost:8000/api/v1/finance?year=abcd" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
# คาดหวัง: {"detail": [{"loc": ["query", "year"], ...}]}

# 409 — เพิ่ม coordinator ซ้ำ
curl -s -X POST http://localhost:8000/api/v1/admin/coordinators \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username": "existing@example.com"}'
# เรียกซ้ำ 2 ครั้ง → ครั้งที่ 2 ต้องได้ 409 Conflict
4. OpenAPI / Swagger
มี auto-generated docs ผ่าน FastAPI /docs และ /redoc พร้อม schema ครบถ้วน
P2Pass

คืออะไร

OpenAPI Specification (เดิมชื่อ Swagger) คือมาตรฐานการเขียน API documentation ที่ machine-readable FastAPI generate spec นี้อัตโนมัติจาก code แล้วแสดงเป็น interactive UI ที่ทดสอบ API ได้โดยตรงจาก browser

ทำไมถึงสำคัญ

Developer ใหม่เข้าใจ API ได้ทันทีโดยไม่ต้องอ่าน code Frontend สามารถ generate TypeScript types จาก OpenAPI spec ได้อัตโนมัติ ลด human error จากการ copy-paste type definition

สถานะในโปรเจกต์ ✓

/api/docs — Swagger UI interactive  ·  /api/redoc — ReDoc readable  ·  /api/openapi.json — machine-readable spec

นอกจากนี้ยังมี static openapi.yaml ใน backend root สำหรับ version control

ทุก endpoint มี summary, response_model, responses dict ครบ ทำให้ doc มีข้อมูลสมบูรณ์

วิธีทดสอบ

  • เปิด browser: http://localhost:8000/api/docs → ต้องเห็น Swagger UI พร้อม endpoint ทั้งหมด
  • เปิด browser: http://localhost:8000/api/redoc → ต้องเห็น ReDoc
  • ดาวน์โหลด spec: curl -s http://localhost:8000/api/openapi.json | python3 -m json.tool | head -30
# ตรวจว่าทุก endpoint มี summary และ response_model
curl -s http://localhost:8000/api/openapi.json \
  | python3 -c "
import sys, json
spec = json.load(sys.stdin)
paths = spec['paths']
for path, methods in paths.items():
    for method, detail in methods.items():
        if method in ('get','post','patch','delete'):
            print(f'{method.upper()} {path}: {detail.get(\"summary\",\"NO SUMMARY\")}')
"
5. Pagination & Filtering
ทุก list endpoint ต้องรองรับ cursor-based pagination, sorting, และ filtering
P2Pass

คืออะไร

Pagination คือการแบ่งผลลัพธ์เป็นหน้าๆ — cursor-based ใช้ pointer ไปยัง record สุดท้ายแทนหน้าเลข (เสถียรกว่าเมื่อข้อมูลเพิ่ม) Filtering คือการกรองข้อมูลด้วย query parameter เช่น year, month, gl_group

ทำไมถึงสำคัญ

ถ้า list endpoint ส่งข้อมูลทั้งหมดในครั้งเดียว เมื่อข้อมูลมีแสนรายการ response จะใช้ memory มากและช้ามาก cursor-based pagination ทำให้ response size คงที่ไม่ว่าข้อมูลจะโตแค่ไหน

สถานะในโปรเจกต์ ✓

Coordinator list pagination (SQL-level): GET /admin/coordinators รองรับ page, page_size (1–100), q (ILIKE search), active (bool filter) — ผ่าน COUNT(*) + LIMIT/OFFSET ใน PostgreSQL ตอบกลับเป็น PaginatedResponse[CoordinatorResponse] พร้อม total, total_pages

Finance/IO/Budget top_n (Python-level slicing): GET /finance, GET /budget, GET /io รองรับ top_n (1–500) เพื่อจำกัดจำนวน rows ในทุก table array — ใช้ post-cache slicing ที่ endpoint layer ดังนั้น cache entry เดิมยังใช้ได้ทุก top_n

Filtering: year, month_from, month_to, gl_group, cost_center, q ✓

// Coordinator list
GET /api/v1/admin/coordinators?q=john&active=true&page=2&page_size=10
→ { success, data: [...], page: 2, page_size: 10, total: 45, total_pages: 5 }

// Finance table slicing
GET /api/v1/finance?year=2025&top_n=20
→ table_by_gl[:20], table_by_cost_center[:20], ...ทุก table key

วิธีทดสอบ

# ทดสอบ pagination — coordinator list
curl -s "http://localhost:8000/api/v1/admin/coordinators?page=1&page_size=5&active=true" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
# คาดหวัง: data มี <= 5 items, field: page, page_size, total, total_pages

# ทดสอบ search filter
curl -s "http://localhost:8000/api/v1/admin/coordinators?q=test" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "
import sys,json; r=json.load(sys.stdin)
print('total results for q=test:', r.get('total'))
"

# ทดสอบ top_n — finance data
curl -s "http://localhost:8000/api/v1/finance?year=2025&top_n=5" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "
import sys,json; r=json.load(sys.stdin)
# ดูจำนวน rows ใน table_by_gl ต้อง <= 5
tbl = r['data'].get('table_by_gl', [])
print('table_by_gl rows:', len(tbl), '(คาดหวัง <= 5)')
"
6. API Request Validation
ใช้ Pydantic schema validation ทุก request body และ query parameter
P1Pass

คืออะไร

การตรวจสอบ input ทุกตัวก่อนเข้า business logic ได้แก่ type checking (int ต้องเป็น int), range validation (year ต้องอยู่ระหว่าง 2000-2100), required fields, และ max length ก่อนที่ code จะเริ่มทำงาน

ทำไมถึงสำคัญ

ป้องกัน garbage data เข้า database, ลด bug ใน business logic, และเป็น first line of defense ด้าน security (ป้องกัน oversized input, unexpected types) FastAPI + Pydantic ทำให้ validation เป็น declarative ไม่ต้องเขียน if-else เอง

สถานะในโปรเจกต์ ✓

Pydantic v2 ครอบคลุมทุก endpoint: FinanceQueryParams validate year (2000-2100), month (1-12), q (max 200 chars) · CoordinatorCreate validate username · EntraLoginRequest, DraftLoginRequest validate request body

FastAPI auto-return 422 Unprocessable Entity พร้อม field-level error detail เมื่อ validation fail

วิธีทดสอบ

# ทดสอบ year ต่ำกว่า range (2000-2100)
curl -s "http://localhost:8000/api/v1/finance?year=1999" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
# คาดหวัง: 422 + detail บอก field "year"

# ทดสอบ month ออกนอก range (1-12)
curl -s "http://localhost:8000/api/v1/finance?year=2025&month_from=13" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
# คาดหวัง: 422

# ทดสอบ missing required field ใน request body
curl -s -X POST http://localhost:8000/api/v1/auth/draft-login \
  -H "Content-Type: application/json" \
  -d '{}' | python3 -m json.tool
# คาดหวัง: 422 + detail บอก field ที่ขาด
7. Response Envelope
Standardize response format: { data, meta, error } เพื่อให้ client parse ได้สม่ำเสมอ
P2Pass

คืออะไร

Response envelope คือ wrapper format ที่สม่ำเสมอทุก endpoint เช่น {"success": true, "data": {...}} แทนที่จะส่ง raw object บางครั้งและ {"error": "..."} อีกครั้งหนึ่ง ทำให้ frontend เขียน generic response handler ชุดเดียวได้

ทำไมถึงสำคัญ

Frontend สามารถเขียน generic response handler ชุดเดียว แทนที่จะต้องรู้ว่า endpoint ไหนส่ง format ไหน ลด bug จากการ handle response ผิด format ทำให้ code frontend clean ขึ้นมาก

สถานะในโปรเจกต์ ✓

schemas/common.py มี APIResponse[T]{success, data} และ ErrorResponse{success, error, detail} — ใช้ครบทุก endpoint แล้ว:

  • Finance / Budget / IO: {"success": true, "data": {kpis, tables...}} — endpoint layer wrap หลัง cache
  • Auth (login, entra-login, draft-login): response_model=APIResponse[TokenResponse] → {"success": true, "data": {token, role, ...}}
  • Auth /me: response_model=APIResponse[UserInfo] → {"success": true, "data": {username, role, ...}}
  • Coordinator POST/PATCH: response_model=APIResponse[CoordinatorResponse] → {"success": true, "data": {...}}
  • Coordinator GET (list): PaginatedResponse มี success + data + pagination meta ✓
  • Error responses: {"success": false, "error": "..."} ✓
// ทุก success endpoint
{ "success": true, "data": <payload> }

// Coordinator list (pagination meta ที่ top level)
{ "success": true, "data": [...], "page": 1, "page_size": 20, "total": 45, "total_pages": 3 }

// ทุก error
{ "success": false, "error": "message" }

วิธีทดสอบ

# ตรวจ success envelope
curl -s http://localhost:8000/api/v1/auth/me \
  -H "Authorization: Bearer $TOKEN" | python3 -c "
import sys,json; r=json.load(sys.stdin)
assert r.get('success') == True, 'missing success:true'
assert 'data' in r, 'missing data key'
print('envelope OK:', list(r.keys()))
"

# ตรวจ error envelope
curl -s http://localhost:8000/api/v1/auth/me | python3 -c "
import sys,json; r=json.load(sys.stdin)
# FastAPI HTTPException format
print('error keys:', list(r.keys()))
"

# ตรวจ pagination envelope
curl -s "http://localhost:8000/api/v1/admin/coordinators" \
  -H "Authorization: Bearer $TOKEN" | python3 -c "
import sys,json; r=json.load(sys.stdin)
for k in ('success','data','page','page_size','total','total_pages'):
    print(f'{k}: {r.get(k, \"MISSING\")}')
"
8. CORS Configuration
กำหนด allowed origins อย่างเข้มงวด ไม่ใช้ wildcard * ใน production
P1Pass

คืออะไร

CORS (Cross-Origin Resource Sharing) คือ browser security mechanism ที่กำหนดว่า website ไหน (origin) สามารถเรียก API ได้ ถ้าไม่ตั้งค่า browser จะ block request จาก domain อื่น ถ้าตั้ง * (wildcard) แสดงว่าทุก website เรียก API ได้ ซึ่งเป็น security risk

ทำไมถึงสำคัญ

ถ้า API ใช้ cookie-based auth หรือ Authorization header wildcard CORS อนุญาตให้ malicious website ดึงข้อมูลด้วย credentials ของ user ที่กำลัง login อยู่ (CSRF-like attack) การระบุ origin ที่ชัดเจนป้องกันปัญหานี้

สถานะในโปรเจกต์ ✓

main.py:69-76 ใช้ settings.get_allowed_origins() แทน ["*"]

รองรับทั้ง comma-separated: ALLOWED_ORIGINS=http://localhost:5173,https://app.example.com และ JSON array format อนุญาตเฉพาะ GET, POST, PATCH, DELETE, OPTIONS เท่านั้น

วิธีทดสอบ

# ทดสอบ CORS — origin ที่อนุญาต (ต้องได้ header ตอบกลับ)
curl -s -I -X OPTIONS http://localhost:8000/api/v1/auth/me \
  -H "Origin: http://localhost:5173" \
  -H "Access-Control-Request-Method: GET" \
  | grep -i "access-control"
# คาดหวัง: Access-Control-Allow-Origin: http://localhost:5173

# ทดสอบ CORS — origin ที่ไม่อนุญาต (ต้องไม่มี CORS header)
curl -s -I -X OPTIONS http://localhost:8000/api/v1/auth/me \
  -H "Origin: https://malicious-site.com" \
  -H "Access-Control-Request-Method: GET" \
  | grep -i "access-control"
# คาดหวัง: ไม่มี Access-Control-Allow-Origin header ตอบกลับ

ตรวจสอบ ALLOWED_ORIGINS ใน .env ว่ามีแค่ origin ที่ถูกต้อง ไม่ใช่ *
