1. ETL / Data Import Process
กระบวนการ import ข้อมูลจาก ERP ไปยัง PostgreSQL มี error handling และ retry mechanism
P2Fail

คืออะไร

ETL (Extract, Transform, Load) คือกระบวนการ: (1) Extract ดึงข้อมูลจาก ERP source (2) Transform แปลง format, clean, validate (3) Load บันทึกลง PostgreSQL table erp_transactions กระบวนการนี้ควรมี scheduled run, error handling, และ idempotent (run ซ้ำได้โดยไม่ duplicate)

ทำไมถึงสำคัญ

Finance dashboard แสดงข้อมูลจาก ERP ถ้ากระบวนการ import ไม่ reliable ข้อมูลที่แสดงจะไม่ครบหรือผิดพลาด ผู้บริหารตัดสินใจบนข้อมูลเก่าหรือผิด ซึ่งส่งผลกระทบต่อการเงินองค์กร

สถานะในโปรเจกต์ — ยังไม่มี

ข้อมูลใน erp_transactions table มีอยู่แล้ว (จาก ERP) แต่ไม่มี documented ETL process ในโปรเจกต์นี้ ไม่ชัดเจนว่าข้อมูลมาจากไหนและ update บ่อยแค่ไหน

สิ่งที่ต้องทำ

  • Document ETL process ที่ใช้อยู่ปัจจุบัน (ถ้ามี): ใครรัน, บ่อยแค่ไหน, เอาข้อมูลจากไหน
  • ถ้ายังไม่มี: สร้าง ETL script พร้อม: idempotent upsert, error logging, retry บน failure
  • เพิ่ม monitoring: รู้เมื่อ ETL run ล้มเหลว (alert ไป email/Line)
  • เพิ่ม data freshness indicator ใน dashboard: แสดง "ข้อมูล ณ วันที่ ..."
# ตัวอย่าง upsert pattern (idempotent)
INSERT INTO erp_transactions (gl_id, fiscal_year, amount, ...)
VALUES (%(gl_id)s, %(year)s, %(amount)s, ...)
ON CONFLICT (gl_id, fiscal_year)
DO UPDATE SET amount = EXCLUDED.amount, updated_at = NOW();
2. Data Validation Rules
ตรวจสอบ data quality ก่อน import: range check, format check, referential integrity
P2Partial

คืออะไร

Data validation rules คือ rules ที่ตรวจสอบว่าข้อมูลที่จะ import เข้า DB ถูกต้องตาม business rules ได้แก่: (1) Format check: fiscal_year เป็น 4 หลัก, amount เป็น numeric (2) Range check: fiscal_month ระหว่าง 1-12 (3) Referential check: cost_ctr_id มีอยู่ใน master table

ทำไมถึงสำคัญ

"Garbage in, garbage out" — ถ้า import ข้อมูลผิดเข้า DB แล้วค่อยมา detect ทีหลัง เสียต้นทุนมากกว่าการ validate ก่อน import นอกจากนั้น finance data ที่ผิดอาจส่งผลกระทบต่อการรายงานทางการเงิน

สถานะในโปรเจกต์ — บางส่วน

มี DB-level constraints: NOT NULL, FOREIGN KEY, CHECK บน migration แต่ไม่มี application-level pre-import validation หรือ data quality report

-- จาก migration: DB-level validation มีอยู่
ALTER TABLE erp_transactions
  ADD CONSTRAINT chk_fiscal_month CHECK (fiscal_month BETWEEN 1 AND 12);
-- แต่ไม่มี pre-import validation script

สิ่งที่ต้องทำ

  • เพิ่ม pre-import validation script ที่ check data ก่อน insert (fail fast)
  • สร้าง data quality report: "import X rows, rejected Y rows, reason: ..."
  • เพิ่ม Pydantic model สำหรับ validate แต่ละ row ก่อน insert
  • เก็บ rejected rows ใน import_errors table เพื่อ review ภายหลัง
3. Reconciliation Process
ตรวจสอบความถูกต้องระหว่างข้อมูลใน dashboard กับ ERP source เป็นระยะ
P3Fail

คืออะไร

Reconciliation คือกระบวนการ cross-check ว่าข้อมูลใน PostgreSQL ตรงกับ ERP source หรือไม่ เช่น ยอดรวมใน dashboard ต้องเท่ากับยอดรวมใน ERP report ถ้า reconcile ไม่ผ่าน แสดงว่ามีปัญหาใน ETL หรือ transformation

ทำไมถึงสำคัญ

แม้จะมี ETL ที่ดี ก็ยังอาจเกิด bug ใน transformation ที่ทำให้ตัวเลขผิดโดยไม่รู้ตัว Reconciliation เป็น "double-check" ที่ catch ปัญหาเหล่านี้ ก่อนที่ผู้บริหารจะเห็นตัวเลขผิดใน dashboard

สถานะในโปรเจกต์ — ยังไม่มี

ไม่มี reconciliation process ไม่มีการ cross-check ระหว่าง dashboard data กับ ERP source เป็นระยะ

สิ่งที่ต้องทำ

  • สร้าง scheduled job ที่ compare aggregate sum ระหว่าง PostgreSQL กับ ERP ทุกสัปดาห์
  • ถ้า reconcile ไม่ผ่าน (difference > tolerance): alert ทันที
  • เขียน reconciliation report: แสดง expected vs actual พร้อม difference
  • เก็บ reconciliation history เพื่อ audit
# ตัวอย่าง reconciliation check
SELECT fiscal_year, SUM(amount) as dashboard_total
FROM erp_transactions
GROUP BY fiscal_year;
-- compare กับ ERP report total
-- ถ้า |dashboard_total - erp_total| > threshold → alert
